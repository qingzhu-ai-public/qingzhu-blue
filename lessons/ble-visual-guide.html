温度计和手机，是怎么说上话的

这节课不绕弯子。桌上就两样东西：一个蓝牙温度计，一部手机。目标只有一个——让手机屏幕显示出温度计测到的温度。它们之间没有线，靠无线电交流。我们按顺序看它们一来一回到底做了什么。

难度：零基础约 15 分钟含交互演练配套：Android 开发指南
1广播 / 扫描先被发现
2建立连接专属通道

4订阅写 CCCD

开场桌上的两样东西

温度计里有一块蓝牙芯片，手机里也有一块。两块芯片用同一种「语言」——低功耗蓝牙（BLE）——就能交流。这种交流分两种角色：温度计这种提供数据、等人来连的叫外设 Peripheral；手机这种主动去找、发起连接的叫中心设备 Central。你写的 Android App，指挥的就是手机这一块芯片。

接下来五步，就是这两块芯片从「互不相识」到「温度上屏」的全部过程。每一步都标出真实术语，学完这一课，你再去看 API 文档就知道每个接口在干嘛。

第 1 步广播与扫描：先让手机发现温度计

温度计还没连上任何手机，它怎么让手机知道自己存在？办法是：每隔一段时间，向外发一小段无线电信号，信号里写着「我叫 XiaoWen-T，我提供温度数据」。这个动作叫广播 Advertising。它不针对谁，附近任何在监听的设备都能收到。

手机这边，App 调用扫描接口，让蓝牙芯片监听这些信号。每收到一个广播，系统就回调一次，把设备名、信号强度、广播内容交给 App。这个动作叫扫描 Scanning。App 把收到的设备列出来——你在界面上看到的设备列表，就是这么来的。

关于广播，记住三个事实：

  • 广播包只有 31 字节。装个设备名和几个服务编号就差不多了，所以广播内容必须精简。
  • 广播间隔是个权衡：发得勤，手机很快发现你，但费电；发得疏，省电，但半天才被看见。常见从几十毫秒到几秒。
  • 收到广播 ≠ 连上设备。这一步只是「看见」，双方还没建立任何关系。
代码入口Android：BluetoothLeScanner.startScan() 开始扫描，每个广播包回调一次 onScanResult()。注意 Android 7.0 起频繁启停扫描会被限流，8.1 起熄屏时不带过滤器的扫描会暂停。详见 广播篇、扫描与过滤。
本步收束：广播 = 温度计周期性对外发信号；扫描 = 手机监听并列出设备。这一步只解决「被发现」。

第 2 步建立连接：开一条专属通道

用户在列表里点了温度计，App 就向它发起连接。双方握手成功后，建立起一条只属于它们俩的通信通道。从这一刻起：

  • 温度计停止广播——已经连上了，不用再对外喊。
  • 双方按约定的节奏交换数据：每隔一个连接间隔醒来一次，有数据就发，没数据就继续睡。
  • 温度计可以要求跳过几个空闲周期（从机延迟），进一步省电。
  • 如果太久没联系上，双方判定连接超时，通道断开。
重点BLE 省电的本质不是不干活，而是约好了才干活。连接间隔越小延迟越低、越费电；从机延迟让没变化的传感器多睡会儿。另外记住：连上 ≠ 能用——通道建好了，但手机还不知道温度计里有哪些数据，这是下一步的事。
代码入口Android：device.connectGatt(context, false, callback) 发起连接，结果从 onConnectionStateChange() 回来。连接参数范围 7.5ms～4s，iOS 另有硬规则。断线重连要当新会话处理。详见 连接篇。
本步收束：连接 = 建立专属通道，停止广播、按周期交流。节奏参数决定快慢与功耗。

第 3 步发现服务：弄清温度计里有哪些数据

连上之后，手机问温度计：「你都能提供什么数据？」温度计回一份清单。这份清单的组织方式有个名字，叫 GATT，它分三层：

  • 服务 Service：一组相关数据。比如「健康温度计」「电池」。
  • 特征 Characteristic：真正装数据的节点。比如「温度测量值」「电量」。
  • 描述符 Descriptor：特征的附加配置。最重要的是 CCCD，下一步讲。

每个节点用 UUID 编号。蓝牙联盟给常见数据定了统一编号：温度测量是 0x2A6E，电量是 0x2A19。所以手机看到编号就知道这是什么数据、什么格式，不用问厂商。

重点手机「把清单要过来看一遍」的动作叫服务发现 discoverServices()。顺序不能乱：先连接，再发现，再操作。没发现服务就去读写，系统找不到目标，必然失败。
代码入口Android：gatt.discoverServices()，完成后 onServicesDiscovered() 回调，再用 getService() / getCharacteristic() 按 UUID 取对象。16 位 UUID 完整形式：0000xxxx-0000-1000-8000-00805F9B34FB。详见 GATT 篇、UUID 篇。
本步收束：GATT = 数据清单，服务 → 特征 → 描述符，UUID 是统一编号。先发现、后操作。

第 4 步订阅与通知：让温度计主动上报

找到温度特征后，手机有三种操作可选：

操作含义适用
Read手机问一次，温度计答一次偶尔看一眼
Write手机向温度计写入配置（如报警阈值）下发设置
Notify / Indicate温度计主动把变化推给手机持续变化的温度

温度一直在变，靠手机一次次 Read 去问，又慢又费电。正确做法是订阅：手机告诉温度计「以后温度一变，你就主动发给我」。这个开关不在特征本身，而在它旁边的描述符 CCCD（编号 0x2902）里。手机往 CCCD 写不同的值：

写入值（小端）含义区别
01 00开启 Notify温度计发了就走，不等确认，快
02 00开启 Indicate每条要等手机回「收到」才发下一条，可靠但慢
00 00关闭停止上报

写成功之后，温度计每次测到新温度，就主动发一个通知过来，手机在回调里收到字节、解析、显示。从此手机不用再问，温度自己上屏。

重点 · 高频故障Android 上订阅要两步都做：setCharacteristicNotification() 打开本地开关，再 writeDescriptor() 把 01 00 写到温度计的 CCCD，等写成功回调。只做第一步，温度计根本不知道你要订阅——这是「收不到通知」的头号原因。
代码入口数据从 onCharacteristicChanged() 回来。2A6E 的格式是小端 sint16、单位 0.01°C：收到 92 09 → 0x0992 = 2450 → 24.50°C。详见 订阅篇。
本步收束：订阅 = 向 CCCD 写 01 00，本地开关 + 远端写入两步都做；之后温度计主动发通知，手机只管收。
