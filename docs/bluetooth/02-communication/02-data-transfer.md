# MTU、L2CAP 与业务分包

两字节的温度读数可以直接放进一次通知。要下载一段历史记录，往往就得拆成多次通知。先算每次操作能带多少字节，再决定接收端怎么把记录拼回去。这一篇把「一次能传多少」的三层长度讲清，再给一套能直接抄的分包协议骨架。

## 先算一条 ATT 操作的预算

LE 的固定 ATT 承载默认 ATT_MTU 为 23 字节。通过 MTU 交换，两端可以按各自的接收能力使用较大的值，**有效值取双方通告值中较小的一个**。手机通告 517、外设通告 185，有效就是 185。应用按平台给出的有效限制发送，还要考虑外设特征和固件自身的长度限制。

MTU 是「一条 ATT PDU 的总长」，操作码和句柄也占空间，留给值的要再扣。

| 单条 ATT 操作 | 该 PDU 中留给值的空间 | 默认 MTU 23 时 |
|---|---:|---:|
| Read Response | `ATT_MTU - 1` | 22 字节 |
| Write Request 或 Write Command | `ATT_MTU - 3` | 20 字节 |
| 单条 Handle Value Notification 或 Indication | `ATT_MTU - 3` | 20 字节 |
| Prepare Write Request | `ATT_MTU - 5` | 18 字节 |

这些数字只描述单条 PDU 的空间。属性值还受规范 512 字节上限和该特征自身的定义约束。ATT 也提供长读（Read Blob 分段续读）、长写（Prepare Write 排队 + Execute Write 提交）流程，使用前要查平台 API 和外设是否支持所需操作。

## 三种长度各管一层

新手最容易把 MTU 和「蓝牙一次能传多少」画等号，实际上有三层长度，各调各的。

```text
应用消息      「一条 37 字节的历史记录」    业务协议定义
    ↓ 拆分
ATT PDU      一条通知最多 MTU-3 字节值     MTU 交换决定
    ↓ 分段
链路层 PDU    默认载荷 27 字节，DLE 后最高 251  数据长度扩展决定
    ↓ 调制
空口          1M / 2M / Coded PHY          PHY 选择决定速率
```

- **ATT_MTU** 限制一条 ATT PDU 的长度。
- **链路层数据长度**影响一条链路层数据 PDU 能承载多少数据。Data Length Extension 调的是这一层，一条 ATT PDU 可以经下层拆到多个链路层包里。
- **应用消息长度**由业务协议定义。历史记录跨多条通知时，接收端要依据应用协议重组。

只提 MTU 不开 DLE，一条 244 字节的通知会被拆成十个 27 字节小包，每包都有链路层头尾和间隔，空口效率很低。两个都调，才有数量级的吞吐变化。这就是为什么[版本与能力演进](#bluetooth/fundamentals/versions)里说 4.2 的 DLE 是分水岭。

L2CAP 把 ATT 等上层协议的数据分送到各自的通道。双方如果都开放了 LE L2CAP 面向连接通道（CoC），也可以把它用于自定义传输，绕开 GATT 的属性模型直接收发数据块。CoC 流控用接收方授予的 credit 限制可发送的帧数。采用前先确认两端的 API 和协议约定（iOS 的 L2CAP 通道接口和 Android 的 Socket 接口形态不同），业务完成回执仍由应用定义。

## 用一条 37 字节记录算一次

假设通知能带 20 字节值，双方约定其中 4 字节用于消息编号和分片信息，每片可放 16 字节记录。37 字节的记录要发 3 片，分别装 `16 + 16 + 5` 字节。

一个够用的片头可以这样设计（示意，字段宽度按业务调）。

```text
字节 0     消息编号（0–255 循环）
字节 1     分片总数
字节 2     分片序号（从 0 起）
字节 3     本片的记录字节数
字节 4 起  记录数据
```

接收端用消息编号和分片序号归组，凑齐并检查长度后再交给业务，超时则清理这条未完成的记录。三个细节别省。

1. **重组超时**。缺一片就永远等下去，缓冲区会被拖死。给每条未完成消息一个期限，过期丢弃并记日志。
2. **重复片处理**。重发或链路重传可能让同一片到两次，按序号覆盖或丢弃，别追加。
3. **编号回绕**。消息编号只有 8 位就只区分 256 条在途消息，同一编号的新旧消息要靠超时清理隔开。

传输连续的历史记录时，可以约定接收窗口或批次确认，给手机处理数据和外设释放缓冲区留出时间。外设无脑连发、手机来不及处理，丢片就发生在两端的缓冲边界上。

## 命令回执与去重

写入采样间隔这类**有副作用的命令**单独约定结果，回执中带命令编号。超时重试沿用同一编号，外设据此识别重复命令，避免重复执行；如果外设无法去重，先读回状态再决定是否补发。

```text
手机 → 设备   命令 42：采样间隔设为 60 s
（回执丢了，手机超时）
手机 → 设备   命令 42：采样间隔设为 60 s   ← 编号不变
设备         查表：42 已执行 → 直接补发回执，不再执行
```

把「传输成功」「命令执行」「业务生效」当三件事分别确认，重连、重试、幂等这些工程问题才有抓手。断线场景的完整讨论在[建连与断线恢复](#bluetooth/fundamentals/connection)。

Android 侧继续看 [MTU、PHY、DLE 与连接参数](#android/development-guide/mtu-phy-dle)和[分包、重组、确认与流控](#android/development-guide/fragmentation-flow)。

## 一句话总结

**MTU 管一条 ATT 消息、DLE 管一个空口包、业务协议管一条完整消息；分包要带编号和序号，重组要有超时，命令重试要靠编号去重。**

## 面试题

1. 手机通告 MTU 517，外设通告 185，一条通知最多带多少字节值？
2. 只把 MTU 提到 247、不开 DLE，吞吐为什么上不去？
3. 设计分包协议时，重组超时和重复片处理各防什么事故？
4. 写配置的命令超时了，为什么重试要沿用同一命令编号？
5. ATT 长写和自定义分包协议，各适合什么场景？

### 参考答案

1. 有效 MTU 取小者 185，通知值空间 185-3 = 182 字节。
2. 链路层默认载荷 27 字节，一条大 ATT PDU 被拆成多个小包，每包都有开销和调度间隔，空口效率低。MTU 和 DLE 要配合。
3. 超时防缺片后无限等待、缓冲区耗尽；重复片处理防重传导致数据重复拼接、记录错乱。
4. 命令可能已执行只是回执丢失。同编号让外设识别重复命令，补发回执而不重复执行，保证幂等。
5. 长写是 ATT 标准流程，适合写一个较长的属性值且两端都支持；自定义分包适合流式数据、历史记录、需要业务级确认和流控的场景。
