# 从扫不到到收不到　按通信阶段排障

温度页没更新，先找最后一步成功的记录。手机可能一直没收到广播，也可能已收到通知，只是把温度字节按错误的格式解析了。两种问题在界面上看起来一样，能用的证据完全不同。这一篇给你一套按阶段收证据的排障方法，以及每种证据去哪里拿。

## 先定位阶段，再找证据

一条链路五道关：广播、连接、发现、订阅、业务。先问「最后一步成功的记录是什么」，把问题钉在一个阶段里，再按下表取证。

| 现象 | 先找的证据 | 下一次怎么验证 |
|---|---|---|
| 扫不到设备 | 是否有该设备的原始广播，是否被过滤 | 把设备移到接收端附近，短时间去掉过滤，用另一台已知能扫描的设备交叉检查 |
| 能扫到但连不上 | 广播是否可连接，连接请求和完成状态各是什么 | 确认设备是否被其他客户端占用，重新扫描获取当前地址与广播状态 |
| 已连接但找不到特征 | 本次服务发现完成状态和实际返回的 UUID 列表 | 核对固件版本和服务表，检查服务变更或客户端缓存 |
| 能读但收不到通知 | 特征属性、本地监听是否启用、CCCD 设置结果 | 完成订阅后触发一个新的读数，同时查看外设发送日志和手机接收日志 |
| 写入报权限错误 | 失败的 ATT 操作、错误码与当前链路的安全状态 | 对照特征权限检查是否需要加密、认证或应用授权 |
| 少量数据正常，大数据出错 | 有效 MTU、每片长度、分片序号、接收窗口 | 在单片上限前后各测一次，再验证重复片、缺片和重组超时 |
| 写入响应成功，界面却显示超时 | 外设是否执行，业务回执的命令编号是否匹配 | 读回配置或核对设备日志，确认命令结果后再决定是否重发 |

几个高频根因值得单独点名。

- **扫不到**：设备被另一台手机连着（大多数外设同时只接受一个连接，被连走后停止广播）；广播间隔太长而扫描窗口太短；过滤条件里的 UUID 根本不在广播里。
- **连不上**：手机缓存的地址过期（设备换了 RPA）；连接请求发出时设备恰好休眠或已被占用，HCI 原因码 `0x3E`。
- **找不到特征**：固件升级改了服务表，客户端还在用缓存；Android 上表现为服务列表陈旧，需要触发缓存刷新。
- **收不到通知**：只做了本地登记没写 CCCD，或反过来；绑定设备重连后 CCCD 残留导致时序错位。

## 一次测试留下一条时间线

排障的原材料是日志，日志的质量决定排障速度。一次连接用同一个**会话编号**，一条业务命令用同一个**命令编号**，重连后换新会话编号。这样超时或迟到的回调属于哪一次尝试，一眼可见。

一条够用的时间线长这样。

```text
14:02:01.120  S3  扫描到目标  地址=7A:..  RSSI=-58  可连接=是
14:02:01.340  S3  发起连接
14:02:01.980  S3  链路建立    interval=50ms
14:02:02.210  S3  服务发现完成  找到温度特征 handle=0x0012
14:02:02.350  S3  CCCD 写入受理
14:02:02.480  S3  CCCD 写入成功
14:02:05.500  S3  收到通知    6A 09 → 24.10°C
14:02:35.480  S3  断开        reason=0x08
```

记录手机系统版本、外设固件版本、每一步的时间和结束状态。没有这份时间线，「偶现收不到」永远只是传说；有了它，偶现问题变成「断开前 30 秒无通知，reason 0x08」这样可查的事实。

## 三层日志各看什么

应用日志对不上时，往下挖一层。

| 层 | 工具 | 能确认什么 |
|---|---|---|
| 应用 | 自己打的日志 | 业务状态机走到哪、回调带什么值 |
| HCI | Android 开发者选项的蓝牙 HCI Snoop；iOS 的 PacketLogger | 主机下发了什么命令、控制器回了什么事件，ATT 字节原文 |
| 空口 | nRF Sniffer、Ellisys 等抓包器 | 实际发射的广播和连接数据，双方谁没按约定出现 |

HCI 日志适合确认「请求发没发、系统回没回」；空口抓包适合确认「设备到底发没发、时序对不对」。空口能看到多少取决于捕获条件，链路加密后载荷不可读，但包时序和长度仍然可见。需要共享日志时，先处理设备标识及业务数据。

Android 上采集 HCI 日志的完整步骤见[抓包、HCI Snoop 与日志诊断](#android/development-guide/hci-log)，错误码对照查 [GATT 错误码与真机故障](#android/development-guide/gatt-errors)。

## 在外设和客户端之间交叉验证

变量隔离是硬件排障的基本功。用同一台手机换一台已知正常的外设，再用同一台外设换一台已知正常的手机。每次只改一边，并保持固件、距离和操作顺序可比较。

| 结果 | 指向 |
|---|---|
| 换手机才复现 | 手机侧：机型、系统版本、厂商策略 |
| 换外设才复现 | 外设侧：固件、硬件批次 |
| 怎么换都复现 | 共有约定：广播格式、服务表、协议文档本身 |
| 怎么换都不复现 | 环境或时序：干扰、距离、竞争连接，回到时间线找规律 |

手边没有第二台外设时，用另一部手机跑 nRF Connect 的外设模拟，或做本指南的[双机实验](#bluetooth/lab/nrf-connect-lab)，先把「已知正常的一端」造出来。

## 一句话总结

**先找最后一步成功的记录把故障钉在一个阶段，再按阶段取证；会话和命令编号让日志可归因，HCI 和空口抓包负责往下挖，交叉验证负责分离变量。**

## 面试题

1. 「界面不更新」可能是哪两个完全不同阶段的问题？各用什么证据区分？
2. 设备昨天能扫到今天扫不到，列出三个可能根因和对应的验证动作。
3. HCI 日志和空口抓包各适合回答什么问题？加密后空口还能看到什么？
4. 换了三台手机都复现同一故障，下一步查哪里？

### 参考答案

1. 可能根本没收到通知（订阅/链路阶段），也可能收到了但解析错（业务阶段）。看接收回调有没有进来、原始字节是什么，即可区分。
2. 被其他手机连走（查设备连接状态/断开其他客户端）；地址轮换后过滤条件失配（去掉过滤看原始广播）；广播或扫描时序对不上（设备调短广播间隔、手机连续扫描再试）。
3. HCI 回答「主机发了什么、控制器回了什么」；空口回答「设备实际发了什么、时序如何」。加密后载荷不可读，但包的时序、长度、方向仍可见。
4. 故障在两端共有的约定里：广播格式、服务表、协议文档、固件行为。从协议文档和固件日志查起。
