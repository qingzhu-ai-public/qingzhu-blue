Pain Points

「连上、发指令、收回复」，
哪一步都埋着坑

对接一个 BLE 设备，看起来只是「连上、发指令、收回复」。但真要落地，下面这些坑一个都躲不掉——而且只在真机上、设备一多之后才暴露

01

扫描慢 / 假死

亮屏后系统扫描「注册成功但不再投递」；没有会话治理，列表看起来还在，设备其实不会再出现。

02

连接慢 / 假在线

低功耗设备 14 秒才回调连接；硬断电时系统又不通知你，界面永远显示「已连接」。

03

发数据慢 / 串包

同一台设备并发发两条指令，应答会串包、丢失；大包、MTU、写类型和传输窗口各自有坑。

04

多设备连不稳

多台同时连会撞车；不同手机的蓝牙栈能力不同，写死连接数迟早出事。

05

多协议重复实现

每接一类设备就复制一套扫描、连接、重试和错误模型；最后没人说得清到底哪套 SDK 拥有蓝牙资源。

这些问题，青竹 BLE 全部吃进了 core——不是给你一堆零件自己拼，而是变成 SDK 的内部策略。你面对的，是一套任务 API。

The API

六个入口，
覆盖任务式 BLE 全流程

从扫描、提交、意图排队到多设备调度和协议扩展。没有一个方法是「内部细节」——你不需要知道连接池，不需要管 worker，不需要写重连逻辑

01

startScan｜扫描先有结果

就像开收音机扫台——转到哪儿听到哪儿，周边设备先列出来

开发者用它做「设备发现页」：时长、RSSI、名称、协议和 stableId 都可以过滤
ScanOptions时长 / RSSIstableId 去重
02

submit｜只给 MAC 也能开工

就像把任务单投进前台——不用先找到人，系统自己找

开发者用它做「批量添加」：设备未知或地址会变，内核自动寻人、连接、发送
自动寻人占位任务连上即发送
03

QTask｜一台设备一个任务

就像每台设备一张进度卡——做到哪一步、为什么失败都看得见

开发者用它做「任务列表」：状态、进度、结果、错误和终态统一展示
状态 / 进度错误 / 结果取消 / 删除
04

executeIntent｜重复操作不互相覆盖

就像排队办事——正在办的先办完，新来的领号

开发者用它做「反复点击」：发送中再连接、连续发送，都有明确结果
有界队列BUSY / CLOSED命令级回调
05

setMaxConnections｜多设备批量调度

就像给车队发通行证——建连排队，传输按窗口放行

开发者用它做「多设备项目」：串行建连、连接容量、传输窗口和批次反馈
串行建连自适应容量批次学习
06

ProtocolPlugin｜换设备只接协议

就像给同一台引擎换喷油嘴——底层不动，协议自己装

开发者用它做「新设备接入」：扫描识别、稳定身份、心跳和连接步骤都归插件
扫描识别稳定身份心跳 / 连接步骤

差别一句话说清：设备未知 / 地址会变 → submit + 自动寻人；设备已在手 → QTask 直接执行；要批量 → 任务池 + 多设备调度；要接新设备 → 注册 ProtocolPlugin。

Zero Config · Pluggable

零配置能用，
想定制全有口子

core 是引擎，你的设备协议是插件。先保证「什么设备都能连」，再谈定制——要改的地方都有干净的口子，没有「改 core 源码」这条路

✓

零配置开箱即用

什么都不配也能扫、连、读写：默认就是标准 connectGatt + 自动发现服务，不配任何 UUID、PHY、MTU，就能浏览周边设备——等价于你熟悉的 nRF Connect。

⚙

ScanOptions 可调

扫描时长、最低 RSSI、名称前缀、协议和 stableId 都可以过滤；QingzhuSdk.settings() 统一管理传输、心跳、重连等全局参数，配错直接报错，不静默失效。

✚

协议是插件

对接一台新设备，只实现 ProtocolPlugin：广播识别、稳定身份、编解码、心跳和连接步骤，常见场景不改 core 一行代码；覆盖不到还有连接步骤逃生舱。

↗

可二次封装

core 用 implementation 依赖，门面只做薄封装和类型适配，就能出公司自己命名的 SDK；core 升级，外围 SDK 直接获得新能力，不需要复制一套蓝牙栈。
