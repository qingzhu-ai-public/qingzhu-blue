扫描与过滤：扫描 API 全景与系统限制

Android 给 BLE 扫描提供了一整套 API：从拿扫描器、建过滤、调扫描参数，到回调交付、后台 PendingIntent，再到系统强加的权限门和限流阀。这一课把每个类、每个方法、每个常量逐一讲清，并给出官方依据。学完你能回答：为什么加了过滤设备消失、为什么扫描悄悄没结果、为什么后台扫不到。

第 1 步扫描 API 全景：一次扫描经过什么

先把地图铺开。一次 BLE 扫描，从你的 App 到空中无线电，要经过四层；结果再原路返回。系统在其中两道关口卡你：权限门（没权限就没结果）和限流阀（启停太频、扫太久就降级）。

类职责引入
BluetoothManager / BluetoothAdapter拿适配器、查硬件能力、拿扫描器18 / 21
BluetoothLeScanner扫描的启动 / 停止 / 冲刷入口21
ScanFilter找什么：按广播字段过滤21
ScanSettings怎么找：功耗、回调方式、批处理、PHY21
ScanCallback怎么交付：逐条 / 批量 / 失败21
ScanResult / ScanRecord看到了什么：设备、信号、广播内容21
PendingIntent 版扫描进程不在也能被结果唤醒26
本步收束：一次扫描 = 找什么（Filter）× 怎么找（Settings）× 怎么交付（Callback），中间隔着权限门和限流阀。

第 2 步拿到扫描器，认清老 API

2.1 现代入口：BluetoothManager → Adapter → LeScanner

// 推荐路径：先 Manager 再 Adapter
val manager = context.getSystemService(BluetoothManager::class.java)
val adapter = manager.adapter          // 不支持蓝牙时为 null
val scanner = adapter?.bluetoothLeScanner  // 蓝牙关闭时为 null！
if (scanner == null) { /* 提示开蓝牙，而不是崩溃 */ }
重点getBluetoothLeScanner() 在蓝牙未开启时返回 null，这是官方文档明确写的。每次扫描前都要判空，别缓存一个可能失效的 scanner。

2.2 能力查询：先问硬件支不支持

方法问什么引入
isOffloadedFilteringSupported()过滤能否下沉到控制器硬件（FIRST_MATCH / MATCH_LOST 依赖它）21
isOffloadedScanBatchingSupported()能否硬件批处理（reportDelay > 0 依赖它）21
isLeCodedPhySupported()能否扫 LE Coded（远距离）PHY26
isLe2MPhySupported() / isLeExtendedAdvertisingSupported()2M 高速 / 扩展广播能力26

2.3 老 API：startLeScan（认识即可，别用）

// API 18 引入，API 21 起废弃。没有过滤、没有参数、不能批处理
adapter.startLeScan { device, rssi, scanRecord -> /* 全收 */ }
adapter.stopLeScan(callback)

它只能「全收」，费电且无法后台。维护老代码时认得它，新代码一律用 BluetoothLeScanner。

2.4 别和经典蓝牙发现混淆

adapter.startDiscovery() 是经典蓝牙的 inquiry，约 12 秒、极费电，和 BLE 扫描是两套东西，不能同时扫（官方指南明确）。连接经典设备前还要 cancelDiscovery()。本课只讲 BLE。

本步收束：Manager→Adapter→LeScanner，判空；先查硬件能力；startLeScan 已废弃；startDiscovery 是经典蓝牙，别混用。

第 3 步startScan 家族：六个方法逐一讲

方法作用引入
startScan(callback)默认参数、无过滤，全收21
startScan(filters, settings, callback)主力：带过滤和参数，结果走回调21
startScan(filters, settings, pendingIntent)后台：结果经 PendingIntent 投递，可唤醒进程；返回 int（0 成功）26
stopScan(callback)停止，须传同一个 callback 实例21
stopScan(pendingIntent)停止 PendingIntent 扫描26
flushPendingScanResults(callback)立刻冲刷控制器里积压的批处理结果21

3.1 主力用法：带过滤 + 限时停止

val cb = object : ScanCallback() {
  override fun onScanResult(type: Int, r: ScanResult) {
    val dev = r.device; val rssi = r.rssi
    val record = r.scanRecord   // 原始广播字节
  }
  override fun onScanFailed(code: Int) { /* 见第 4 步错误码 */ }
}
val filters = listOf(ScanFilter.Builder()
  .setServiceUuid(ParcelUuid.fromString("00001809-0000-1000-8000-00805F9B34FB")).build())
val settings = ScanSettings.Builder()
  .setScanMode(ScanSettings.SCAN_MODE_LOW_LATENCY).build()
scanner.startScan(filters, settings, cb)
handler.postDelayed({ scanner.stopScan(cb) }, 10_000)  // 官方建议：找到就停，永远限时

官方指南两条铁律：找到目标立刻停扫；永远给扫描设时限，不要循环扫。filters 和 settings 都允许传 null（等价无过滤 / 默认参数）。

3.2 后台用法：PendingIntent 版

val intent = Intent(context, ScanReceiver::class.java)
val pi = PendingIntent.getBroadcast(context, 0, intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_MUTABLE)
val ret = scanner.startScan(filters, settings, pi)  // ret==0 才算成功
// Receiver 里取结果：
val results = intent.getParcelableArrayListExtra<ScanResult>(BluetoothLeScanner.EXTRA_LIST_SCAN_RESULT)
val err = intent.getIntExtra(BluetoothLeScanner.EXTRA_ERROR_CODE, -1)
  • 进程被杀也能被匹配结果唤醒，适合「设备出现就干活」的场景。
  • 三个 extra：EXTRA_LIST_SCAN_RESULT（结果列表）、EXTRA_ERROR_CODE（错误码）、EXTRA_CALLBACK_TYPE（回调类型），均 26。
  • 坑：创建 PendingIntent 时不要用 FLAG_CANCEL_CURRENT，否则 stopScan(pi) 可能停不掉（官方文档警告）。
  • Android 15 起，强行停止应用会取消它的所有 PendingIntent，包括扫描——被强停后扫描就没了。
本步收束：前台用 callback 版并限时；后台用 PendingIntent 版并检查返回值；stop 要配对；别用 FLAG_CANCEL_CURRENT。

第 4 步ScanCallback 与六个错误码

回调何时触发
onScanResult(callbackType, result)每收到一条匹配广播（逐条模式）
onBatchScanResults(results)批处理模式（reportDelay>0）攒够一批后
onScanFailed(errorCode)扫描启动失败
码常量含义与对策公开
1ALREADY_STARTED同参数扫描已在跑 → 别重复 start21
2APPLICATION_REGISTRATION_FAILEDApp 注册失败 → 常伴随限流，退避重试21
3INTERNAL_ERROR栈内部错误 → 重试 / 重启蓝牙21
4FEATURE_UNSUPPORTED低功耗扫描特性不支持 → 换参数21
5OUT_OF_HARDWARE_RESOURCES硬件过滤资源耗尽 → 减少过滤条件33
6SCANNING_TOO_FREQUENTLY启停过频被限流 → 等 30s 再 stop+start33
重点 · 最阴的坑限流发生时，很多版本根本不回调 onScanFailed：扫描「看起来启动了」，但一条结果都没有，只有 logcat 里一行包名为「?」的 scanning too frequently。AOSP 框架把 scannerId 置为 -2 后直接静默。所以不能只靠 onScanFailed 判断扫描健康，要监控结果流：长时间没结果就主动重启。
本步收束：三个回调、六个错误码；5/6 到 API 33 才公开；限流常静默，靠结果流监控兜底。

第 5 步ScanResult 与 ScanRecord：看到的是什么

5.1 ScanResult 字段

字段 / 方法含义引入
deviceBluetoothDevice，后续连接的入口21
rssi信号强度 dBm，有效范围 [-127, 126]，波动大21
timestampNanos开机起算的纳秒时间戳（对齐 SystemClock.elapsedRealtimeNanos），不是 wall clock21
scanRecord广播 + 扫描响应的合并内容21
primaryPhy / secondaryPhy主 / 次广播信道 PHY（1M / Coded）26
isLegacy / isConnectable是否传统广播 / 是否可连接26
advertisingSid / txPower / periodicAdvertisingInterval扩展广播集 ID / 发射功率 / 周期广播间隔26
dataStatus数据完整 / 截断（DATA_COMPLETE / DATA_TRUNCATED）33

5.2 ScanRecord：把广播字节解析成人话

方法拿到什么引入
getDeviceName()广播里的名字（可能来自扫描响应）21
getServiceUuids()广播里声明的服务 UUID 列表21
getManufacturerSpecificData()厂商 ID → 数据（SparseArray）；传 ID 取单条21
getServiceData()服务 UUID → 数据（Map）；传 UUID 取单条21
getTxPowerLevel() / getAdvertiseFlags()发射功率 / 广播标志21
getBytes() / parseFromBytes()原始字节 / 从字节重建（排查神器）21
getServiceSolicitationUuids()服务征询 UUID29
getAdvertisingDataMap()AD Type → 原始数据 的完整 Map（配 DATA_TYPE_* 常量）33
// 例：解析 iBeacon（厂商 ID 0x004C = Apple）
val mfr = result.scanRecord?.getManufacturerSpecificData(0x004C)
// 排查「过滤为什么没命中」：先打印原始字节
val raw = result.scanRecord?.bytes?.joinToString(" ") { "%02X".format(it) }
本步收束：timestampNanos 是开机时钟；名字 / UUID 必须真在广播里；排查先 getBytes 看 RAW。

第 6 步ScanFilter：全部过滤条件逐一讲

Builder 方法过滤依据引入
setDeviceName(name)广播 / 扫描响应里的名字21
setDeviceAddress(mac)MAC 地址。随机地址会轮换，隐私设备别用它21
setServiceUuid(uuid[, mask])广播声明的服务 UUID，mask 可只比部分位21
setServiceData(uuid, data[, mask])服务数据（如 BTHome 0xFCD2）21
setManufacturerData(id, data[, mask])厂商数据（如 iBeacon 0x004C）21
setServiceSolicitationUuid(uuid[, mask])服务征询 UUID29
setAdvertisingDataType(type)按 AD Type 存在性过滤（SIG 分配值）33
setAdvertisingDataTypeWithData(type, data, mask)按 AD Type + 内容过滤33

组合语义：同一个 ScanFilter 内多个条件是与（都要满足）；列表里多个 ScanFilter 之间是或（命中任一即交付）。空列表 = 全收。支持 offload 时过滤在控制器硬件完成，不匹配的广播不唤醒 CPU。

重点 · 高频坑服务 UUID 过滤失效，多半是 UUID 根本没写进广播（设备连接后才暴露服务）。名字过滤失效可能是名字在扫描响应里平台没交付。RSSI 过滤慎用（波动大）。排查先去掉全部过滤看原始字节。

勾「按厂商数据」→ 设备消失，因为广播里根本没有厂商数据

    

    
本步收束：过滤字段必须真实存在于广播；条件内与、条件间或；筛不到先去过滤看 RAW。

  


  

    
第 7 步ScanSettings：全部扫描参数逐一讲

    
7.1 setScanMode：功耗与速度的档位

    

      
模式值行为引入

      
SCAN_MODE_OPPORTUNISTIC-1不自己开扫，搭别人扫描的便车被动听结果23

      
SCAN_MODE_LOW_POWER0默认档，最省电；App 不在前台时被强制用这档21

      
SCAN_MODE_BALANCED1折中，适合前台较长时间扫描21

      
SCAN_MODE_LOW_LATENCY2最高占空比，最快发现；只建议前台短时使用21

    

    
「档位」本质是扫描窗口 / 扫描间隔这对参数。一组实测参考值（不同厂商 / 版本会调）：LOW_POWER ≈ 140/1400ms（听 10% 时间）、BALANCED ≈ 183/730ms（≈25%）、LOW_LATENCY ≈ 100/100ms（≈100%）。窗口短于广播间隔时会漏包——这就是低功耗档「发现慢」的物理原因。

    
7.2 其余参数

    

      
Builder 方法作用引入

      
setCallbackType(flags)ALL_MATCHES(1) 每条都报；FIRST_MATCH(2) 首次出现报；MATCH_LOST(4) 消失报；可按位或。后两者需硬件 offload 支持23

      
setMatchMode(mode)AGGRESSIVE 弱信号也尽快报；STICKY 要更强信号 / 更多次 sightings 才报23

      
setNumOfMatches(n)ONE / FEW / MAX：硬件匹配上报的广播条数档位23

      
setReportDelay(ms)0 立即报；>0 批处理，攒到 max(ms, 5000) 或缓冲满才走 onBatchScanResults；需硬件批处理支持21

      
setLegacy(bool)默认 true 只收传统（≤4.2）广播；false 才收 BLE 5 扩展广播26

      
setPhy(phy)仅 legacy=false 时生效：1M / CODED / ALL_SUPPORTED(255)；选不支持的 PHY 会启动失败26

      
setScanType(type)ACTIVE（等扫描响应）/ PASSIVE（收到即报，不等响应）36.1

      
setRssiThreshold(dbm)只收 RSSI ≥ 阈值的广播，[-127,126]36.1

    

    
setScanResultType 已废弃（只剩 FULL 一种），不用管。MATCH_LOST 在各厂商上表现不稳，工程上更可靠的做法是自己用定时器清理超时未见设备（如 10 秒没再见到就移除）。

    
val settings = ScanSettings.Builder()
  .setScanMode(ScanSettings.SCAN_MODE_BALANCED)
  .setCallbackType(ScanSettings.CALLBACK_TYPE_ALL_MATCHES)
  .setReportDelay(0)            // 前台逐条；后台批处理改 >0
  .setLegacy(false)             // 要收 BLE5 扩展广播才关
  .build()

    
本步收束：前台短扫 LOW_LATENCY、长扫 BALANCED、后台 LOW_POWER；批处理走 onBatchScanResults；扩展广播要 legacy=false。

  


  

    
第 8 步权限门与限流阀：系统不告诉你的规则

    
8.1 权限随版本变（详见 B2）

    

      
版本扫描需要什么

      
≤ 5.1（API ≤22）BLUETOOTH / BLUETOOTH_ADMIN，安装即授

      
6.0 – 9（23–28）+ 位置权限（粗即可）+ 系统位置开关打开，否则一条结果都没有

      
10 – 11（29–30）位置必须 ACCESS_FINE_LOCATION

      
12+（31+）BLUETOOTH_SCAN；声明 neverForLocation 可免位置，否则仍需 FINE；连接另需 BLUETOOTH_CONNECT

    

    
neverForLocation 是「我绝不拿蓝牙推导位置」的强声明，代价是部分信标类广播数据会被系统滤掉——扫信标的项目要实测。

    
8.2 三道限流阀

    
    
      
  • 启停限流（7.0 起，未写进官方文档）：30 秒内 startScan 超 5 次即被限，常静默（见第 4 步）。冷却后需 stop+start 才恢复，不会自动恢复。
    • 
      
  • 熄屏暂停（8.1 起，官方文档写明）：不带过滤的扫描在熄屏时停止交付，亮屏恢复。所以后台扫描必须带 ScanFilter。
    • 
      
  • 长扫降级（13 QPR1 起覆盖带过滤扫描）：扫描运行超过 scan_timeout_millis，ScanManager 把它悄悄降到低功耗档（无过滤的降到 opportunistic），不通知 App，回调还在只是变稀。AOSP 默认曾为 30 分钟，Android 15 起降到 10 分钟，实测有的机型 5 分钟。可用 adb shell device_config get bluetooth scan_timeout_millis 查。
    • 
    

    
工程对策长扫场景：在超时前主动重启扫描（如每 4 分钟，留足余量），重启计入 5 次/30s 配额所以别太频；同时监控结果流，久无结果就重启。后台再叠加 PendingIntent + 前台服务（见 B10）。
