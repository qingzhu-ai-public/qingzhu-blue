# BLE 建连、连接参数与断线恢复

手机收到传感器的可连接广播后，可以发起连接。链路建立后，两端按约定的时序交换数据。这时手机还得找到温度特征，并按业务需要完成订阅或认证，界面才有理由显示「可以读温度」。这一篇讲连接建立后发生的事：时序怎么定、就绪怎么判、断了怎么接回来。

## 连接是一连串按时的约会

BLE 连接不是一条一直开着的线。链路建立后，两端约定一个节奏，每隔一段时间同时醒来交换数据，这个时刻叫**连接事件**（Connection Event）。事件之间双方都可以睡觉。没有数据要发时，事件可以短到只交换一个空包确认「我还活着」。

```text
连接事件      连接事件      连接事件      连接事件
   │             │             │             │
   ▼             ▼             ▼             ▼
───█─────────────█─────────────█─────────────█───→ 时间
   └── interval ──┴── interval ──┘
   手机和外设同时醒来，交换数据包，然后各自睡去
```

三个参数决定这个节奏。

| 参数 | 范围 | 影响 |
|---|---|---|
| Connection Interval | 7.5 ms – 4 s（6.2 起可低至 375 µs） | 相邻连接事件锚点的间隔。短则交互快、唤醒频繁；长则省电、延迟大 |
| Peripheral Latency | 0 – 499 | 外设没数据时可以连续跳过的事件数。空闲时少唤醒，有数据仍可参加事件 |
| Supervision Timeout | 100 ms – 32 s | 链路在这段时间内收不到有效数据包就判定连接丢失 |

三个参数有约束：超时时间必须大于 `(1 + latency) × interval × 2`，否则外设合法地跳过几个事件就会被误判断线。举例：interval 50 ms、latency 4，外设最长可以 250 ms 不出现，超时就至少要设 500 ms 以上，实践中留更大余量。

参数由谁定？外设可以表达自己的偏好（Preferred Connection Parameters），但**决定权在 Central**，手机系统按自己的策略接受或调整。iOS 对外设请求的参数有明确的接受范围，写在 Apple 的 Accessory Design Guidelines 里；Android 各厂商策略也不一致。所以同一台传感器在两台手机上实测到的间隔可能不同，这不是故障，是策略。

估算吞吐时还要看每次连接事件能交换多少包。缩短连接间隔可能有帮助，也可能因双方调度、干扰或设备处理能力而达不到预期。用目标设备记录实际参数和收发速率，再决定怎么取舍。

## 业务什么时候放行

「已连接」是链路层的事，「可以读温度」是业务的事，中间还有几步。把就绪拆成能观察的条件。

1. 确认本次连接已建立，记录连接或请求编号。
2. 找到需要的服务、特征和订阅描述符。遇到安全要求则按设备协议建立所需安全状态。
3. 手机启用本地接收，并确认服务端接受订阅配置。若固件有应用层握手，等到握手完成再开放对应操作。

这些步骤的顺序会随设备要求变化。例如某个设备会在读特征时才要求加密。日志把每个阶段和错误分别记下来，才能区分连接超时、发现失败和订阅失败。界面上「连接中」转圈转到天荒地老，多半是把这几步混成了一个状态。

## 断开时发生了什么

断开不是只有一种。HCI 层的原因码值得记几个，日志里见到能直接定位方向。

| 原因码 | 含义 | 常见场景 |
|---|---|---|
| `0x08` | Connection Timeout | 走远了、干扰、外设死机，监督超时内没收到包 |
| `0x13` | Remote User Terminated | 对端主动断开，比如外设关机或固件主动断链 |
| `0x16` | Terminated by Local Host | 本机主动断开，App 调了 disconnect |
| `0x3E` | Failed to be Established | 连接请求发了，但首个连接事件没成功，常见于设备刚被别的手机连走 |

`0x08` 和 `0x3E` 是排查重点：前者说明链路曾经活着后来丢了，后者说明根本没建立起来。两者的排查方向完全不同，前者查距离、干扰、外设功耗策略，后者查广播状态和连接竞争。

## 断开后重新建立什么

收到断开事件就让旧连接退出业务队列，丢弃属于旧会话的迟到回调。重新连接后按平台与设备能力确认服务和安全状态，恢复本地监听，再检查服务端订阅配置。

订阅状态有个容易踩的细节：按 GATT 规范，服务端为**已绑定**客户端保留 CCCD 配置，未绑定客户端每次连接都回到默认值（关闭）。也就是说绑定设备重连后，设备可能还记得上次的订阅、直接开始发数据，而手机本地监听还没登记，数据就丢了。两种情况下，应用都要确认新会话已经能接收数据，别假设「上次订过这次就不用订」。

重连期间先标记待确认的操作。有副作用的命令可能已经在外设执行，只是回执还没回来。要再次下发，先查询设备状态，或按[命令编号与去重规则](#bluetooth/communication/data-transfer)重试。盲目重发「开始加热」这类命令，事故就是这么来的。

重连策略本身也要设计：立即重试几次、退避多久、什么条件下放弃并提示用户。无脑循环重连既费电又可能撞上系统限制。Android 侧的完整做法见[连接生命周期](#android/development-guide/connection-lifecycle)和[线程、状态机、命令队列与取消](#android/development-guide/thread-state-machine)。

## 一句话总结

**连接是按间隔赴约的时序，参数由 Central 拍板；链路建立只是第一步，发现、安全、订阅都确认了才算就绪；重连要当作新会话，订阅和未完成的命令都重新核对。**

## 面试题

1. interval 100 ms、latency 9，外设最长多久不出现仍是合法的？监督超时至少要设多少？
2. 外设请求 interval 15 ms，两台手机实测分别是 15 ms 和 50 ms，是故障吗？
3. 日志里断开原因 `0x08` 和 `0x3E` 分别指向什么排查方向？
4. 已绑定设备重连后，为什么可能「设备在发、手机收不到」？
5. 断线前发出的「写配置」命令没收到回执，重连后直接重发有什么风险？

### 参考答案

1. 最长 (1+9)×100 = 1000 ms。超时必须大于 2×1000 = 2000 ms，实践留更大余量。
2. 不是。参数决定权在 Central，各系统有自己的接受策略，iOS 和 Android、不同厂商都可能不同。
3. `0x08` 是链路建立后监督超时，查距离、干扰、外设是否死机或休眠过度；`0x3E` 是连接从未建立，查广播是否还在、设备是否刚被其他客户端连走。
4. 服务端为绑定客户端保留了 CCCD，重连后直接按旧订阅发数据；手机本地监听还没重新登记，数据被丢弃。重连后要重新完成本地登记并确认订阅状态。
5. 命令可能已在外设执行，只是回执丢了。直接重发可能重复执行。先读回设备状态，或用同一命令编号让外设去重。
