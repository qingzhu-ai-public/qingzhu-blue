# 配对、绑定、加密与地址隐私

手机连上后能读温度，写采样间隔却返回安全相关错误。先查看这个特征的访问权限。固件可以允许读数公开，同时要求配置写入使用加密链路，或要求客户端通过特定级别的认证。这一篇把蓝牙安全的几个状态拆开，讲清配对怎么发生、密钥怎么保存、地址为什么会变，以及恢复出厂后那类「昨天还好好的」故障。

## 把安全状态分开记

「配对了」在日常用语里是一句话，在协议里是好几件事。

| 状态 | 表示什么 |
|---|---|
| 已连接 | 两端的蓝牙链路已建立 |
| 已配对（Pairing） | 两端建立了用于保护通信的共享密钥 |
| 已绑定（Bonding） | 两端保存了配对所得的密钥等信息，供以后重连使用 |
| 当前链路已加密 | 本次连接已启用链路层加密 |
| 应用已授权 | 设备或服务已允许当前使用者执行某项业务操作 |

配对是过程，绑定是保存，加密是本次连接的状态。配对可以不绑定（密钥用完就丢，下次重来）；绑定的设备重连后不自动加密，要用保存的密钥**重新启用**加密。抓日志时把这几个状态分别记录，才能区分密钥丢失、加密还没启动，以及属性权限不够这三种完全不同的故障。

## 配对怎么发生

配对由安全管理器（SM）执行，分两代方案。

- **LE Legacy pairing**：4.0/4.1 时代的方案，密钥交换本身可被被动窃听破解，今天只该出现在存量设备上。
- **LE Secure Connections**：4.2 引入，用 ECDH（P-256 椭圆曲线）交换密钥，被动窃听拿不到密钥。新产品的默认基线。

两代方案下都有几种**配对方式**，由双方的输入输出能力（IO Capability）决定。

| 方式 | 用户看到什么 | 中间人（MITM）防护 |
|---|---|---|
| Just Works | 无感知或一个确认框 | 无 |
| Numeric Comparison | 两端显示同一个 6 位数字，用户核对 | 有（Secure Connections 下） |
| Passkey Entry | 一端显示、另一端输入 6 位数字 | 有 |
| OOB | 通过 NFC 等带外通道交换信息 | 取决于带外通道 |

关键认知：**加密不等于防中间人**。Just Works 也能建立加密链路，但配对过程没有 MITM 防护，攻击者理论上可以在配对瞬间冒充双方。对温度读数这可能无所谓，对门锁、支付类操作就不行。产品要求抵抗这种风险时，按硬件能力选择带防护的配对方式，并把「链路已加密」和「业务已授权」分开验证。

配对过程产生的密钥各有用途：**LTK** 用于重连后启用加密；**IRK** 用于解析对方的隐私地址；CSRK 用于数据签名（较少用）。绑定的本质就是把这几把钥匙存下来。

## 设备地址变了还能认出来吗

BLE 外设可以用**可解析私有地址**（RPA），地址每隔一段时间变化，典型是 15 分钟量级（6.1 起更新时机随机化，更难被追踪）。目的是防止附近的陌生接收器长期追踪这台设备。

地址看起来随机，但持有对方 **IRK** 的一侧能解析出「这是不是我认识的那台设备」。绑定过程中双方交换了 IRK，所以绑定后的重认不靠地址字面值。应用能拿到什么标识取决于平台 API 和系统策略：Android 通常给地址，iOS 给的是系统生成的 per-device 标识，同一台外设在两台 iPhone 上标识不同。

工程结论：设备列表、历史数据和任务记录需要长期关联时，使用**产品定义的稳定标识**。可以在完成可信连接或业务认证后读取设备序列号并建立映射。若打算把固定序列号直接放进明文广播，先评估是否允许附近的接收器长期追踪这台设备——很多产品刻意不这么做。设备名、RSSI 和广播里的明文字段均可用于筛选，授权要有独立依据。

## 联调时测一次恢复出厂

一类高频故障：外设恢复出厂了，手机还留着旧绑定。外设丢了密钥，手机拿旧 LTK 去加密，失败；表面现象是「连上了但读写报错」或「反复弹配对」。反过来，手机侧删除绑定、外设还留着旧密钥，同样对不上。

用同一对设备把这四个场景各测一遍。

1. 首次配对：记录双方各存了什么。
2. 断开重连：确认用保存的密钥启用加密，不再走完整配对。
3. 外设恢复出厂：手机侧应检测到密钥失效，引导用户删除旧绑定再重新配对。
4. 手机侧取消绑定：外设侧的旧密钥如何清理，是否需要用户操作。

记录两侧各自清除了什么，设备标识和用户归属也按产品流程重新确认。恢复出厂路径不设计，客诉里一半的「连不上」都来自这里。

Android 的操作与边界见[配对与 LE 安全](#android/development-guide/pairing-security)和[地址轮换与隐私](#android/development-guide/address-privacy)。

## 一句话总结

**配对建密钥、绑定存密钥、加密是本次连接的状态；Just Works 有加密没防中间人；地址会变是隐私设计，认设备靠 IRK 和业务标识；恢复出厂要两侧一起清。**

## 面试题

1. 已绑定的设备重连后，链路自动就是加密的吗？
2. Just Works 配对建立了加密链路，能防中间人攻击吗？产品该怎么补？
3. 同一台 BLE 外设在两台 iPhone 上拿到的标识不同，是 bug 吗？
4. 外设恢复出厂后手机读写报错，根因是什么？产品流程怎么设计？
5. LTK 和 IRK 各干什么用？

### 参考答案

1. 不是。绑定保存了密钥，重连后要用保存的 LTK 重新启用加密，启用前链路仍是明文。
2. 不能。Just Works 缺少 MITM 防护。按硬件能力改用 Numeric Comparison 或 Passkey 等带防护的方式，业务侧再加独立授权。
3. 不是。iOS 给应用的是系统生成的标识，按手机隔离；这是平台隐私策略。跨手机关联设备要用产品自己的稳定标识。
4. 外设丢了绑定密钥，手机还拿旧 LTK 加密，密钥不匹配。设计上要检测密钥失效，引导删除旧绑定重新配对，并把恢复出厂列入测试用例。
5. LTK 用于重连后启用链路加密；IRK 用于解析对方的可解析私有地址，认出设备身份。
