连接与重连：didConnect 与断开恢复

connect 异步，等 didConnect；断开走 didDisconnectPeripheral。iOS 没有 Android 式 autoConnect 参数，但 connect 请求永不超时、设备出现即连——这本身就是重连机制。这一课把连接 API、四个连接状态、options 键、iOS 17 自动重连与连接事件监听逐一讲清。

第 1 步connect 与三个回调、四个状态

central.connect(peripheral, options: nil)
// didConnect / didFailToConnect / didDisconnectPeripheral
API / 回调作用引入
connect(_:options:)发起连接；请求永不超时，设备不在场就一直挂着（pending）iOS 5
cancelPeripheralConnection(_:)取消活跃或挂起的连接请求iOS 5
didConnect连接建立；接下来才能 discoverServicesiOS 5
didFailToConnect(error:)连接请求失败（如设备拒绝、参数非法）iOS 5
didDisconnectPeripheral(error:)断开；error 为 nil = 本地主动断，非 nil = 意外断（超时/链路丢失）iOS 5

1.1 CBPeripheral.state：四个连接状态

状态含义
.disconnected没连（或已断开）
.connectingconnect 已发出，等 didConnect（可能挂很久）
.connected已连接，可发现/读写
.disconnectingcancel 已发出，等 didDisconnect

枚举 CBPeripheralState 自 iOS 7 可用。retrieve 取回的对象先查 state：已 .connected 就跳过 connect 直接发现服务。

1.2 connect options 键

键作用引入
CBConnectPeripheralOptionNotifyOnConnectionKeyApp 被挂起时连接成功，系统弹提示横幅iOS 6
CBConnectPeripheralOptionNotifyOnDisconnectionKeyApp 被挂起时断开，系统弹提示横幅iOS 5
CBConnectPeripheralOptionEnableAutoReconnect链路掉线后系统自动发起重连（见第 2 步）iOS 17
本步收束：connect 异步，三回调分管成功/失败/断开；四状态查 peripheral.state；options 按需加。

第 2 步重连三条路：pending connect、手动 retrieve、iOS 17 自动

let known = central.retrievePeripherals(withIdentifiers: [savedID])
known.forEach { central.connect($0) }
// 或 retrieveConnectedPeripherals(withServices:) 找系统已连的

2.1 路一：connect 本身就是「等设备出现」

对不在场的设备 connect 不会失败也不会超时：请求挂在系统里，设备一出现就自动完成连接并回调 didConnect。所以「断开后立刻再 connect」就是最简单的重连——不需要设备在场。这也是后台恢复（C9）的基础：挂起的 connect 能让系统在有事件时唤醒你的 App。

// 意外断开 → 立即重挂 connect（设备回来即连上）
func centralManager(_ c: CBCentralManager, didDisconnectPeripheral p: CBPeripheral, error: Error?) {
  clearLocalState(p)                 // 清订阅登记，重连当新会话
  if error != nil { c.connect(p, options: nil) }   // 意外断才自动重连
}

2.2 路二：冷启动用 retrieve 找回

App 重启后对象没了，但系统还记得设备：存下 identifier，启动时 retrievePeripherals(withIdentifiers:) 取回再 connect；设备可能已被其他 App 连到系统，用 retrieveConnectedPeripherals(withServices:) 查（两者均 iOS 7，见 C3）。

2.3 路三：iOS 17 系统级自动重连

central.connect(p, options: [CBConnectPeripheralOptionEnableAutoReconnect: true])
// iOS 17+：链路掉线后系统自动重新发起连接，App 无需在 didDisconnect 里手动 connect

2.4 监听对端发起的连接/断开：registerForConnectionEvents

// iOS 13+：外设主动连上来 / 断开 / 订阅变化，也能收到回调（配合后台恢复很有用）
central.registerForConnectionEvents(options: [
  .peripheralUUIDs: [savedUUID]      // CBConnectionEventMatchingOption
])
func centralManager(_ c: CBCentralManager, connectionEventDidOccur event: CBConnectionEvent,
                    for p: CBPeripheral) {
  // .peerConnected / .peerDisconnected / .notifyEnabled …
}
重点 · 与 Android 对照Android 用 autoConnect=true 让栈慢慢等；iOS 的 connect 天生就是「无限等待」语义，没有 autoConnect 参数。iOS 17 的 EnableAutoReconnect 补上的是「掉线后系统自动再连」，对应 Android 栈层行为。重连当新会话：重新 discoverServices、重新 setNotifyValue，别沿用旧对象登记。
本步收束：保存 identifier，retrieve 再 connect；意外断立即重挂；iOS 17 可交给系统自动重连；重连新会话。

第 3 步cancelPeripheralConnection：取消与共享连接

主动断用 cancelPeripheralConnection；系统可能因共享连接不立即断。断开后清理本地订阅登记，重连重新核对。

central.cancelPeripheralConnection(peripheral)
// 取消 pending 请求：立即生效，不再有 didConnect
// 取消活跃连接：本地会话结束（didDisconnect error=nil），
// 但若其他 App / 系统服务还连着同一设备，物理链路可能保持
  • cancel 是「本地退订」不是「强制断链」：BLE 连接是系统级共享资源，别的 App 还在用就不会断物理链路。
  • 挂起的 connect 也能 cancel：不想要「设备出现即连」的语义时，记得取消，否则设备一出现你的 App 可能被后台唤醒。
  • 断开后清理：订阅登记、写队列、分包缓冲都按会话作废；重连后重新发现、重新订阅、重新核对 CCCD。
  • 自己加超时：connect 永不超时是特性也是坑——前台连接建议自配 10–15 秒定时器，超时 cancel 并提示用户。
本步收束：主动断 cancel；共享链路可能不断；重连重新核对订阅；前台连接自配超时。
