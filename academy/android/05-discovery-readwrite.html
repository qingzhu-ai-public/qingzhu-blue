服务发现与读写：一次一操作的排队

连上后 discoverServices 拿到属性表，再读写特征。Android 同一时刻只允许一个未完成的 GATT 操作，必须排队。这一课把属性表模型、发现、读写、writeType、描述符与可靠写逐一讲清，并给出官方依据。

第 1 步属性表模型：服务 → 特征 → 描述符

类关键方法引入
BluetoothGattServicegetUuid / getType / getCharacteristics / getCharacteristic(uuid)18
BluetoothGattCharacteristicgetUuid / getProperties / getDescriptors / getDescriptor(uuid)18
BluetoothGattDescriptorgetUuid / getValue18

properties 常量：PROPERTY_READ / PROPERTY_WRITE / PROPERTY_WRITE_NO_RESPONSE / PROPERTY_NOTIFY / PROPERTY_INDICATE 等，决定该特征允许哪些操作。

本步收束：服务→特征→描述符三层；properties 定操作、permissions 定加密；16 位标准 UUID / 128 位自定义。

第 2 步discoverServices 是异步的

gatt.discoverServices()
override fun onServicesDiscovered(g:BluetoothGatt, status:Int) {
  // status==GATT_SUCCESS 才取对象
  val svc = g.getService(UUID.fromString("00001809-0000-1000-8000-00805f9b34fb"))
  val ch  = svc?.getCharacteristic(UUID.fromString("00002a6e-…"))
}
  • 发现完成前 getService 返回 null；必须等 onServicesDiscovered。
  • 系统会缓存服务表。固件升级改了服务表后缓存可能陈旧，发现结果与预期对不上：可反射调 refresh() 或断开重连触发重新发现。
  • 标准服务变化时设备可发 Service Changed 指示，Android 31+ 有 onServiceChanged 回调。
本步收束：等 onServicesDiscovered 再取对象；缓存陈旧要刷新；留意 Service Changed。

第 3 步一次只提交一条属性操作

// 旧签名（33 起废弃，但仍可用）
ch.value = bytes; gatt.writeCharacteristic(ch)   // 等 onCharacteristicWrite
gatt.readCharacteristic(ch)                      // 等 onCharacteristicRead
// API 33+ 推荐新签名：值直接传入，避免 ch.value 被并发覆盖
gatt.writeCharacteristic(ch, bytes, WRITE_TYPE_DEFAULT)

上一个操作没回调就发下一个，会被丢弃或返回 false。必须排队串行，每项等匹配回调再发下一条。匹配三要素：GATT 实例 + 操作类型 + 特征 UUID。B9 的状态机就是干这个。

操作方法回调引入
读特征readCharacteristic(ch)onCharacteristicRead18
写特征writeCharacteristic(ch[,value,type])onCharacteristicWrite18（新签名 33）
读描述符readDescriptor(desc)onDescriptorRead18
写描述符writeDescriptor(desc[,value])onDescriptorWrite18（新签名 33）
重点API 33 起 read/changed/descriptorRead 新增直接带 value 参数的重载，旧 getValue() 方式废弃——新写法避免回调里读 ch.value 被后续操作覆盖的竞态。
本步收束：一次一操作，等匹配回调（实例+类型+UUID）再发下一条；33+ 用带 value 新签名。

第 4 步writeType：有响应 / 无响应 / 可靠写

writeType对应 ATT确认适用
WRITE_TYPE_DEFAULTWrite Request有 onCharacteristicWrite关键命令
WRITE_TYPE_NO_RESPONSEWrite Command无逐条确认，高频可丢高频可丢数据

可靠写（长写）：需要把多段数据作为原子事务写入时用 beginReliableWrite() → 多次 writeCharacteristic → executeReliableWrite()（或 abortReliableWrite() 放弃），回调 onReliableWriteCompleted。适合超过 MTU 的大块固件/配置。

本步收束：关键命令 DEFAULT；高频可丢 NO_RESPONSE；原子大块用可靠写。
