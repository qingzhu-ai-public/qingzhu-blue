# 多设备调度

## 为什么不能全部同时连

多个 `connectGatt` 同时发起时，手机蓝牙栈和设备端都会被压住：

- 连接更容易超时或假连；
- 设备端可能进入半连接状态；
- GATT 句柄和连接回调更难收口；
- 传输窗口不受控，回包更容易串。

所以建连阶段有**串行闸门**，一次只发起一个连接；连接建立后可以保留多条连接。

## 三个不同的资源

| 资源 | 含义 | 默认 |
|---|---|---|
| 连接容量 | 最多同时保留多少条连接 | 启动体检给出的建议值，上限 7 |
| 传输窗口 | 同时允许多少台设备发送 | 1（串行） |
| 单设备 GATT | 同一台设备内部的操作顺序 | 始终串行 |

它们不是同一个旋钮：连接容量决定「能同时握着几台」，传输窗口决定「能同时发几台」。

## 配置

```java
QingzhuSdk.setMaxConnections(0); // 0 = 用体检建议值；1-N = 手动固定
QingzhuSdk.setMaxTransfers(1);   // 1 = 串行传输
QingzhuSdk.setMaxRetries(3);     // 连接 / 发送 / 寻人失败的重试次数
QingzhuSdk.setMaxPendingIntents(8);

int current = QingzhuSdk.getConcurrency();
```

普通机型建议从「自动连接容量 + 传输窗口 1」开始，目标机型验证稳定后再提高传输并发。

## 并发上限是怎么来的

手机不会告诉你「最多能同时连几台」——Android 没有这个 API。SDK 的做法是：

```text
启动时读系统公开能力（蓝牙 5.0 特性 / Android 版本 / CPU 核数 / 内存）
  → 给一个起始建议值（BLE 5.0 → 7 台，Android 8.0+ → 4 台，老机器 → 2 台）
  → 写进连接池生效
```

这个值只是**起跑点**，估得不准很常见。所以：

- 保守的机型可以先 `setMaxConnections(2)` 手动固定；
- 目标机型实测稳定后再往上加；
- 上限锁在 7，对齐连接池容量和 Android 常见 GATT 上限。

## 自动学习没有接通

早期版本有一个「跑完一批统计成功率、回灌并发建议」的学习器。**批量接口删除后，这条回路断了。**

现状：

- `AdaptiveConcurrency` 仍然保留，但只在启动时用来取建议值；
- `recordBatch()` 还是公开方法，**当前没有任何调用方**；
- 也就是说，运行期不会根据实际成功率自动调并发。

需要自动调的话，得自己在任务完成处统计成功 / 连接失败数，再调 `recordBatch()`。在接回去之前，请把手动配置当作唯一生效的并发设置。

## 效果边界

当前能证明的是任务、队列、终态和取消逻辑有单元测试覆盖；还没有大规模真机矩阵、长期浸泡和不同厂商 ROM 的统计结果。

另外，设备被短时间反复连断后可能自己进入异常（能连上但不响应服务发现），这属于设备端行为，SDK 只能退避等待，不能「修好」它。

不要把「有针对机型的建议值」误解为「所有机型都已调优」。
