分包与流控：maximumWriteValueLength

iOS 用 maximumWriteValueLength(for:) 查单次能写多少，长数据自己切片。withoutResponse 连发靠 canSendWriteWithoutResponse + ready 回调流控。这一课把单包上限、业务分包协议、流控队列完整实现，以及 L2CAP 高吞吐替代路线讲清。

第 1 步maximumWriteValueLength(for:)：两种类型两个答案

let n = peripheral.maximumWriteValueLength(for: .withoutResponse) // = MTU-3
let m = peripheral.maximumWriteValueLength(for: .withResponse)    // 通常 512（系统长写）
API返回引入
maximumWriteValueLength(for: .withoutResponse)ATT_MTU − 3；MTU 23 → 20B，MTU 247 → 244BiOS 9
maximumWriteValueLength(for: .withResponse)通常 512B；超出 MTU 部分系统自动 Prepare/Execute 长写iOS 9
openL2CAPChannel(_:) / CBL2CAPChannel流式通道：拿 InputStream/OutputStream，不再逐包切片iOS 11
  • 连接后再查：MTU 在连接时由系统自动协商（iOS 无 requestMtu），同一设备不同连接结果可能不同；别缓存上次的值。
  • 长写不是免费午餐：withResponse 长写由多个 ATT 往返组成，吞吐低；大文件走无响应写+流控，或干脆 L2CAP。
  • L2CAP 通道：设备固件要支持并公布 PSM；适合音频/固件升级等持续流，GATT 仍负责控制面。
本步收束：按类型查单次上限（iOS 9）；无响应=MTU−3，带响应=512 长写；大流考虑 L2CAP（iOS 11）。

第 2 步业务分包带编号序号

跨多次写的记录要带消息编号+分片序号+长度，接收端重组要超时+去重（同 A7/B8）。iOS 不替你重组，业务协议自定。

// 发送端：按无响应上限切片，每片带协议头
let chunkSize = p.maximumWriteValueLength(for: .withoutResponse) - 4  // 留 4B 头
var seq = 0
for start in stride(from: 0, to: payload.count, by: chunkSize) {
  let piece = payload[start ..< min(start+chunkSize, payload.count)]
  var frame = Data([msgId, UInt8(seq), UInt8(total), UInt8(piece.count)])
  frame.append(piece)
  queue.append(frame)          // 进流控队列，见第 3 步
  seq += 1
}
  • 协议头四件套：消息编号（区分并发记录）、分片序号、总片数、本片长度——接收端缺一样都重组不稳。
  • 重组三兜底：超时（如 2 秒没集齐就丢）、去重（同 msgId 重复片）、乱序（按 seq 排，别假设按序到达）。
  • 送达确认分层：无响应写只保证「发出去了」；关键数据要设备回业务 ACK，或整条记录用 withResponse 写。
本步收束：分包编号序号，重组超时去重；关键记录要业务 ACK。

第 3 步withoutResponse 的 ready 流控：完整实现

while canSendWriteWithoutResponse { write(nextChunk, .withoutResponse) }
// peripheralIsReadyToSendWriteWithoutResponse → 继续发
API作用引入
canSendWriteWithoutResponse发送缓冲有无空位（Bool）iOS 11
peripheralIsReady(toSendWriteWithoutResponse:)缓冲恢复空位时回调配 iOS 11
// 工程完整版：队列 + pump + ready 续发 + 断线清理
var queue: [Data] = []
func pump() {
  while p.canSendWriteWithoutResponse, !queue.isEmpty {
    p.writeValue(queue.removeFirst(), for: ch, type: .withoutResponse)
  }
}
func peripheralIsReady(toSendWriteWithoutResponse p: CBPeripheral) { pump() }
// didDisconnect 时：queue.removeAll()——旧会话的片别再发到新会话
  • canSend=false 硬发的后果：数据可能被静默丢弃，没有任何错误回调——「偶尔丢包」的头号来源。
  • ready 回调可能不来：断线时缓冲作废，靠 didDisconnect 清队列；别死等。
  • iOS 11 以下：没有流控 API，只能限速延时或改 withResponse；新项目最低版本建议 ≥ 11。
  • 背压：队列设上限（如 256 片），满了让业务层等待/丢弃，别无限堆内存。
本步收束：canSend 判断+ready 回调续发，防丢；断线清队列；队列设上限。
