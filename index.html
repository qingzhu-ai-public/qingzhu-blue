Pain Points

蓝牙开发真正难的，
不是「怎么连」

连一台设备的教程遍地都是。真正吃掉工期的是下面这些问题——它们只在真机上、设备一多之后才暴露

01

一次连几台合适？

同时连 7 台，谁先连、超时算多久、失败要不要马上重试——系统对连接数还有上限，撞上去就是整批失败。

02

设备突然掉线怎么办？

是主动断开、信号丢失还是设备重启？重连几次、退避多久、界面上的状态怎么跟真实连接对齐。

03

设备地址变了，怎么找回来？

随机化 MAC 之后，昨天记住的地址今天可能就不对了。刚连上的是同一台设备，还是另一台？

04

一批里有一台连不上，继续吗？

50 台批量配置，第 30 台失败：跳过、重试还是整体中止？中途断了，下次从哪一台续。

这些问题没有标准答案，但每个项目都要重新回答一遍。青竹 Blue SDK 把它们变成 SDK 的内部策略，而不是你的业务代码。

What It Handles

从小到大的活，
一套 SDK 都能接

不是只能干一件事。从连一台设备慢慢调，到同时管一批、批量刷配置、传固件——六类场景共用同一套接口

01

连一台，慢慢操作

就像连蓝牙耳机——连上就一直连着，你什么时候想用就什么时候用

开发者用它做「设备设置页」：连上设备，改改参数，点保存
连接保持GATT 读写通知订阅
02

同时连好几台，随时控制

就像智能家居 App——客厅的灯、卧室的灯、空调一起管着，点哪个控哪个

开发者用它做「设备管理页」：一次连 7 台，每台实时看状态、随时下命令
并发连接池排队与超时状态同步
03

一批设备，挨个刷配置

就像工厂流水线——一批货过来，一个接一个处理，处理完自动换下一个

开发者用它做「批量配置」：门店 50 个电子价签，挨个改价格
任务队列逐台执行断点续做
04

连上后要问一串问题

就像给人做体检——先量身高、再称体重、再测血压，全测完出一张报告

开发者用它做「查询设备信息」：逐个查型号、电量、版本，最后汇总成一份设备档案
顺序任务结果汇总超时兜底
05

给设备升级固件

就像手机系统更新——把新版本传进去，能看到进度条，装完自动重启

开发者用它做「固件升级」：几百 KB 的新固件可靠地传进设备
OTA分包传输进度与续传
06

设备主动汇报

就像微信消息——不用你问，有事它自己推给你

开发者用它做「实时监控」：设备电量低了、按钮被按了，第一时间通知 App
Notify 订阅数据解析事件回调
Inside the SDK

外面几行，
里面是这些

上面六类场景背后，其实是同一批硬骨头。SDK 的追求是：把复杂全包在里面，开发者只写「我要连这几台」「我要发这句话」

连接
并发上限与排队连接超时与重试断线自动重连退避策略地址变更还原
数据
MTU 自动协商分包与重组Notify 去重粘包拆包读写超时兜底
批量
任务队列与串行失败跳过 / 中止断点续做进度与结果汇总
通用
统一错误码前后台与权限适配线程与生命周期可插拔日志

以上是 SDK 的设计范围与目标（Android 先行实现，其余平台按同一套结构铺开）；实际进度以 GitHub 仓库为准。
