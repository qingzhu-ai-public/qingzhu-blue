# 第 22 章　GATT 错误码与真机故障

标签换图失败，用户只看到「蓝牙错误 8」。你去查状态码，有的地方写「连接超时」，有的地方写「授权不足」。先回到日志，找出这个 8 是哪一个方法或回调给你的。

如果它来自 HCI 断开原因，`0x08` 可以表示连接超时。如果来自设备回给属性请求的 ATT 错误，`0x08` 是授权不足。把日志写成 `callback=onConnectionStateChange status=8 (0x08) newState=DISCONNECTED`，至少能看出失败出现在连接这一步。需要确认具体来源时，再对照附近的 HCI 事件或 ATT 响应。

## 找到最后一个成功的动作

先沿着「扫描 → 连接 → 发现 → 写入 → 业务确认」找最后一条成功记录。比如设备已经出现在列表里，随后连接没有成功，就先取连接发起、回调和关闭的日志。查表时从实际停止的那一行开始。

| 现象 | 先取什么证据 | 判断下一步 |
| --- | --- | --- |
| 扫描未发现设备 | 起始结果、是否触发 `onScanFailed`、权限、过滤字段、设备广播时间 | 独立扫描器能否看见原始广播，过滤条件实际在包中是否存在 |
| `connectGatt` 得到句柄却一直没有成功回调 | 设备句柄新鲜度、是否可连接、GATT 代次、超时和关闭日志 | HCI 是否出现连接请求、成功或失败事件 |
| 连接成功但服务为空 | 发现发起的布尔值、`onServicesDiscovered`、服务枚举、固件变更 | 是发现没完成、UUID 写错，还是使用了过期的服务表 |
| 写失败 | API 的立即拒绝、完成回调、特征实例、写类型和长度 | 判断被 Android 拒绝，还是对端给了 ATT Error Response |
| 写成功，业务超时 | 会话就绪状态、CCCD、业务序号、HCI 和设备日志 | 是否发通知、数据是否到手机、应用是否正确重组 |

## 常用状态码，先分清来源再查含义

同一个数字在不同回调里含义不同。下面这张表把最常见的值按来源分开，完整对照在[状态码速查](#android/development-guide/appendix-c-codes)：

| 值 | 出现在哪个回调 | 含义 | 第一步 |
| --- | --- | --- | --- |
| 8（0x08） | `onConnectionStateChange` | HCI 连接超时（链路监督超时） | 查距离、干扰、连接参数和设备是否还在广播/连接 |
| 19（0x13） | `onConnectionStateChange` | 对端主动断开 | 查设备端日志：它为什么断（省电、任务完成、异常） |
| 22（0x16） | `onConnectionStateChange` | 本机 Host 主动断开 | 查自己是否调了 `disconnect()`，或系统回收 |
| 62（0x3E） | `onConnectionStateChange` | 连接建立失败 | 查设备句柄是否新鲜、设备是否可连接 |
| 133（0x85） | 任何 GATT 回调 | 通用内部错误，见下节 | 先定位阶段，再找紧邻系统事件 |
| 5（0x05） | 读写/订阅回调 | ATT 认证不足 | 走配对/绑定流程，见[第 19 章](#android/development-guide/pairing-security) |
| 15（0x0F） | 读写/订阅回调 | ATT 加密不足 | 同上，确认链路已加密 |
| 1 | `onScanFailed` | 同一 callback 已注册 | 检查是否重复 `startScan` |
| 2 | `onScanFailed` | 应用注册失败 | 常见于频繁启停被限流，稍后再试 |
| 6 | `onScanFailed` | 扫描过于频繁 | 见[第 25 章](#android/development-guide/vendor-compat)的平台行为清单 |

日志里把来源写全，查表就不会串。对比这两条：

```text
坏：BLE error 8
好：op=connect gen=3 cb=onConnectionStateChange status=8(0x08) newState=DISCONNECTED elapsed=30012ms
```

第二条一眼能看出：这是第 3 代会话在建连 30 秒后收到链路超时，接下来该查设备侧和无线环境，而不是去翻 ATT 错误表。

## 看到 133 时，从哪里开始查

这份 AOSP 蓝牙栈源码中，`0x85` 定义为 `GATT_ERROR`。平台可能用它报告多种内部或连接流程错误。先确认失败发生在连接、发现或属性操作，再找紧邻的系统事件。可控复测中一次只改变一个变量，例如同一配置换手机，或同一手机换固件。查到源文件里的符号是定位工作的一步，根因仍由日志和可重复现象支持。详见 [状态码速查](#android/development-guide/appendix-c-codes)。

## 什么时候适合再试一次

如果上一轮连不上，先结束旧 GATT。用户仍需要这次操作、设备也仍可用时，再等一段时间重试。缺权限时回到授权，蓝牙关了就等用户开启。用户取消后结束任务。写命令已经发出而结果未知时，先查设备状态或按幂等协议恢复。比如标签可能已经换好图，只是那条确认没回到手机。

## 一句话总结

**错误码要和它出现的阶段一起读，最后一项成功证据会告诉你下一步该查哪里。**

## 面试题

1. 日志里只有 `status=8`，为什么还不能确定根因？
2. 遇到 GATT 133，能否直接说是设备固件有问题？
3. 写请求结果未知，适合直接重发一条新命令吗？

### 参考答案

1. 先补方法或回调名、业务阶段和原始报文。HCI 的 `0x08` 与 ATT 的 `0x08` 含义不同。
2. 133 是一类通用错误。用连接或属性操作阶段、HCI 日志、对端记录和可重复对照来定位。
3. 先查询设备状态或带同一个幂等键重试，避免设备已经做完时再执行一次。
