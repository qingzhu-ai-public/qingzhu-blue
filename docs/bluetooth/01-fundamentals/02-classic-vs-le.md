# 经典蓝牙与 BLE 怎么选

接一台存量串口设备时，说明书可能写着 SPP。换成一台电池供电的温度传感器，说明书上更可能是一组 GATT 服务和特征 UUID。两台设备都叫蓝牙设备，App 要使用的通信接口却完全不同。选错链路，后面所有代码都要重来，所以这一步值得花十分钟想清楚。

## 先问两端支持什么

选型的第一依据不是你的偏好，是设备已经实现了什么。

| 要做的事 | 先确认的能力 |
|---|---|
| 接已支持 SPP 的串口设备 | 设备支持经典蓝牙 BR/EDR 上的 SPP，目标平台也允许应用访问这个 Profile |
| 给存量耳机播放音乐或接听电话 | 耳机和手机是否共享 A2DP 或 HFP 等对应的经典蓝牙 Profile |
| 做电池传感器，需要读数和参数设置 | BLE 是否满足更新频率和功耗要求，双方是否约定了 GATT 接口 |
| 给附近多台接收设备发少量状态 | BLE 广播的载荷和接收延迟是否够用，业务能否容忍漏收 |
| 接 LE Audio 设备 | 两端是否支持相应的 LE Audio Profile 和角色 |

经典蓝牙一侧，应用通常不直接碰协议，而是走系统提供的 Profile 通道。常见的几个先混个脸熟。

| Profile | 干什么用 | 应用怎么接 |
|---|---|---|
| SPP | 串口透传，存量工业设备常见 | Android 用 RFCOMM Socket；iOS 不开放给普通 App |
| A2DP | 立体声音频流 | 系统接管，App 一般只控制播放 |
| HFP | 免提通话 | 系统接管 |
| HID | 键鼠、手柄 | 系统接管 |

注意平台差异：iOS 的普通 App 拿不到 SPP，接经典蓝牙配件要走 MFi 的 External Accessory 框架。同一台 SPP 设备，Android 能直连，iOS 可能根本走不通。这类平台边界在选型阶段就要查清，别等固件定型才发现。

设备标注「双模」，表示支持 BR/EDR 和 LE 两种传输。具体能用哪些 Profile，还要查设备和目标平台。版本号可以帮你查规范，但应用能不能调用某项能力，需要查系统接口并拿目标设备验证，原因在[版本与能力演进](#bluetooth/fundamentals/versions)里讲过。

## 把实际数据量算出来

传感器每分钟更新一次温度，和应用一次下载一天的历史记录，对链路的要求很不一样。把三个数写下来再选。

1. **单次数据量**：一条读数 2 字节，一天的历史记录可能几十 KB。
2. **更新频率**：每分钟一次，还是每秒十次。
3. **能容忍的延迟**：界面晚一秒更新行不行，控制指令必须多久生效。

然后决定读数直接随广播发出，还是建立连接后再传。

**广播路线**适合多台接收设备独立收听。设备按固定间隔发，谁在附近谁就能收，没有连接数限制。某一台接收器漏掉一条读数，等下一条更新就恢复了。代价是传统广播每条只有 31 字节预算，没有逐条确认，也不适合手机向设备写配置。

**连接路线**适合双向交互。手机要设置采样间隔、读历史、收某台设备的实时更新，就建连接走 GATT。代价是设备要维护连接、按连接事件唤醒，功耗上去了，而且大多数外设同时只接受一个连接。

功耗的直觉可以这样建立：广播设备只在发包瞬间醒来，其余时间睡觉；连接设备每个连接事件都要醒来一次，哪怕没有数据。连接间隔 50 ms 意味着每秒醒 20 次。纽扣电池想跑一年，要么拉长间隔、用好外设延迟，要么干脆走广播。

## 吞吐别信规格书，实测

对持续传输的业务，用目标手机和外设实测有效吞吐、断连和功耗。规格里的 PHY 速率只描述物理层：2M PHY 的 2 Mbit/s 是符号速率，应用实际每秒能传多少，还要扣掉协议头、连接事件调度、两端处理速度。

给一个量级感：默认 MTU 23、每次通知带 20 字节值的配置下，应用吞吐通常只有每秒几 KB；MTU 提到 247、开 DLE、用 2M PHY 后，同样的硬件可以到每秒几十 KB 甚至更高。差距一个数量级，所以「传一段固件要多久」这种问题，先问清 MTU、DLE、PHY 和连接间隔，再拿真机测。怎么算每包预算，见 [MTU、L2CAP 与业务分包](#bluetooth/communication/data-transfer)。

## 一个可以照着走的判断顺序

1. 设备已定型：查它支持的 Profile 或 GATT 服务，没得选，按它的来，重点核对目标平台是否开放接口。
2. 设备未定型，数据小、频率低、多接收方：优先广播。
3. 需要双向交互、可靠传输、手机写配置：BLE 连接 + GATT。
4. 音频：存量设备走经典蓝牙 Profile，新产品评估 LE Audio。
5. 持续大流量（如高速透传）：BLE 也能做，但先实测吞吐；真不够再考虑经典蓝牙 SPP 或其他无线方案。

## 一句话总结

**先看设备实现了什么，再算数据量、频率和延迟三个数；小数据多听众走广播，双向交互走连接，音频看 Profile，吞吐以实测为准。**

## 面试题

1. 一台 SPP 串口设备，Android App 和 iOS App 都能直接连吗？
2. 温度传感器每分钟发一次读数，附近十几台手机都要显示，选广播还是连接？说出两个理由。
3. 连接间隔 50 ms 对电池设备意味着什么？想省电可以调哪些参数？
4. 设备标称 2M PHY，应用实测吞吐远低于 2 Mbit/s，可能的原因有哪些？

### 参考答案

1. Android 可以用 RFCOMM Socket 连 SPP。iOS 不向普通 App 开放 SPP，需要 MFi 授权走 External Accessory，选型时就要确认。
2. 选广播。一对多没有连接数限制；设备只发不连，功耗最低；漏收一条可以等下一条恢复，业务能容忍。
3. 每秒要醒来 20 次参加连接事件，空闲时也在耗电。可以拉长连接间隔、用外设延迟跳过空闲事件，或改用广播方案。
4. 协议头和每条 ATT 操作的开销、MTU 仍是默认 23、未开 DLE、连接间隔偏长、对端只支持 1M PHY、两端处理速度跟不上。逐项核对后实测。
