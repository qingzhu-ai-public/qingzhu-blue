# 第 28 章　性能、功耗与稳定性

用户觉得这块标签换图慢，你给 GATT 写方法加了计时，发现每次调用都很快。再往后看，手机把数据送完以后，标签还要保存图片和刷新屏幕。整个等待过程要从按「换图」算到设备确认完成。

先测用户关心的这段时间，再在里面加几个时间点。什么时候扫到，什么时候连上，什么时候可以发，最后什么时候收到设备确认。下一轮优化就能针对真正花时间的地方。

| 指标 | 从哪里到哪里 | 记录方式 |
| --- | --- | --- |
| 首次发现时间 | 开始扫描到首次匹配 | 单调时钟，包含未发现样本 |
| 连接与就绪时长 | 发起建连到连接成功，再到订阅和认证完成 | 分阶段记录成功率与 P50/P95 |
| 有效吞吐 | 单位时间内对端确认的业务字节 | 不计重试、帧头和重复字节 |
| 能耗 | 某一固定任务或一定时长的使用场景 | 比较屏幕、信号、系统策略一致的实验 |
| 长期稳定性 | 多轮连接、传输、取消及恢复后的行为 | 终态分布、超时、重试次数、资源增长 |

## 找到耗时最长的一段，再改一个参数

发现慢时检查广播周期、主包字段和扫描模式。连接阶段慢时看新鲜地址、是否重叠发现、同时发起连接数。已连接后的耗时要分开量服务发现、MTU、CCCD 和设备业务处理。确定卡住的阶段后，每轮只调整一个参数。

假如日志显示大部分时间花在传图片，可以分别试 MTU、PHY、发送窗口和应用帧结构。每次只改一个，统计单位时间内对端确认了多少图片字节，再看失败率和慢任务的耗时。若标签在忙着写闪存，窗口加大以后，更大的队列也可能只是让数据在设备里排得更久。试过高连接优先级后记下实际参数，任务结束再尝试恢复平衡模式。

## 传完要快，平时也要省电

可将用户触发的低延迟扫描限定在短窗口，常驻搜寻采用有效过滤、低功耗模式和必要的批量报告。按用户意图和设备属性选择是否保持连接，限制重连频率。广播端根据产品发现延迟预算设置间隔并验证。

对外发布配置时带上实验条件、样本数、失败和耗时，再和旧配置对照。若全量放开成本高，按机型/固件组合逐步验证。配置的默认并发、重试和超时应该可回退，能通过日志看出这次用的是哪个参数组合。

## 一句话总结

**拿用户实际等了多久做总账，再用每一步的时间和成功率判断优化有没有帮上忙。**

## 面试题

1. 为什么不能用 `writeCharacteristic` 的调用耗时评价换图速度？
2. 加大发送窗口后吞吐指标怎么验证？

### 参考答案

1. 调用的立即结果不包含系统发送、设备确认和屏幕更新。应该统计点击到设备完成确认的端到端耗时。
2. 统计对端确认的业务字节每秒，排除重复和帧头，并对照失败率、尾延迟及功耗。
