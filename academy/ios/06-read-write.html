读与写：withResponse 的取舍

readValue 走 didUpdateValueFor；writeValue 分 withResponse（等 didWriteValueFor）与 withoutResponse（无逐条确认）。这一课把读写 API、两种写的 ATT 本质、MTU 与 maximumWriteValueLength、无响应写流控逐一讲清。学完你能回答：一次最多写多少字节、长数据谁来分包、连发无响应写为什么不丢。

第 1 步readValue → didUpdateValueFor

peripheral.readValue(for: ch)
// didUpdateValueFor characteristic → ch.value
API / 回调作用引入
readValue(for: CBCharacteristic)读特征值；结果更新到 ch.value 并回调iOS 5
readValue(for: CBDescriptor)读描述符（如用户描述 0x2901）iOS 5
peripheral(_:didUpdateValueFor:error:)读到值 / 通知到达，共用此回调iOS 5
  • 值存在对象上：回调里读 ch.value（Data?），不是回调参数直接给数据——这是与 Android（回调带 byte[]）的形态差异。
  • 长值自动分段：值超过 MTU 时系统自动用 Read Blob 续读拼好，App 无感知。
  • 别轮询：能订阅的特征用 setNotifyValue（C7），readValue 只用于一次性取值。
  • error 要查：readNotPermitted / insufficientAuthentication 等 ATT 错误从这里来（C10 配对场景常见）。
本步收束：读和通知共用 didUpdateValueFor 回调；值在 ch.value；长值系统拼。

第 2 步withResponse vs withoutResponse：两种写与 MTU

类型ATT确认引入
.withResponseWrite RequestdidWriteValueForiOS 5
.withoutResponseWrite Command无逐条确认iOS 5
// 关键命令：带响应写，等确认
p.writeValue(configData, for: ch, type: .withResponse)
func peripheral(_ p: CBPeripheral, didWriteValueFor ch: CBCharacteristic, error: Error?) {
  // error == nil：ATT 层接受了；业务生效还要读回或等业务回执
}

// 高频数据：无响应写，先查流控（见第 3 步）
if p.canSendWriteWithoutResponse {
  p.writeValue(chunk, for: ch, type: .withoutResponse)
}

2.1 一次最多写多少：maximumWriteValueLength

API返回引入
maximumWriteValueLength(for: .withoutResponse)ATT_MTU − 3（Write Command 头部占 3 字节）；MTU 23 时只有 20iOS 9
maximumWriteValueLength(for: .withResponse)通常 512：超长值系统自动走 Prepare/Execute 长写iOS 9
let n = p.maximumWriteValueLength(for: .withoutResponse)  // 连接后查询
// 协商 MTU 185 → n = 182；发 1000 字节要自己切 6 片（C8）
重点didWriteValueFor 只确认 ATT 层接受，业务生效要读回或等业务回执。withoutResponse 适合高频可丢，关键命令用 withResponse。iOS 不暴露 requestMtu：MTU 由系统在连接时自动协商（这点与 Android 手动 requestMtu 不同），你只能用 maximumWriteValueLength 查询结果。
本步收束：关键命令 withResponse；成功只到 ATT 层；单包上限查 maximumWriteValueLength（iOS 9）。

第 3 步canSendWriteWithoutResponse：无响应写流控

withoutResponse 连发要看 canSendWriteWithoutResponse，满了等 peripheralIsReadyToSendWriteWithoutResponse 再发，防丢。

API作用引入
canSendWriteWithoutResponseBool：发送缓冲现在有没有空位iOS 11
peripheralIsReady(toSendWriteWithoutResponse:)缓冲从满变空时回调，继续发下一批配 iOS 11
// 标准流控循环：队列 + canSend + ready 回调
func pump() {
  while p.canSendWriteWithoutResponse, let chunk = queue.first {
    queue.removeFirst()
    p.writeValue(chunk, for: ch, type: .withoutResponse)
  }
}
func peripheralIsReady(toSendWriteWithoutResponse p: CBPeripheral) {
  pump()   // 缓冲又有空位，接着发
}
  • iOS 11 之前：没有流控 API，连发无响应写会静默丢包——老代码只能靠延时或改用 withResponse。
  • canSend 为 false 时硬发：数据可能被丢弃且无任何回调，这是无响应写「丢数据」的头号原因。
  • 文档标注说明：peripheralIsReady 的文档页标 iOS 5（协议引入版本），但它与 canSendWriteWithoutResponse 配对使用，实际按 iOS 11+ 对待。
  • 分包与队列的完整工程实现见 C8。
本步收束：无响应写要流控，canSend 为真才发，等 ready 再续；iOS 11 起才有这套 API。
