综合实战：BTHome 温湿度计完整 App

与 Android 板 B14 同一个项目：iPhone 当接收器扫描解析 BTHome 温湿度广播，扫到即显示、不连接不配对；再用教学 GATT 服务练连接与读写，第二台 iPhone（或 Android 手机）当模拟外设。iOS 发不出 BTHome 广播这条平台边界，这一课讲透。

第 1 步BTHome 是什么、规范在哪

BTHome 是 Home Assistant 主推的开放 BLE 传感器广播标准。设备把读数按固定格式塞进广播包，接收端不用连接、不用配对，扫到就能解析。正因为是开放格式，Shelly、Xiaomi 一大批传感器、HA、ESPHome 都直接支持。

资源地址拿什么
官网bthome.io项目入口、设备列表
格式规范bthome.io/format广播结构、设备信息字节、全部对象 ID 表
加密规范bthome.io/encryptionAES-CCM 加密、nonce、防重放
参考解析器github.com/Bluetooth-Devices/bthome-blePython 解析器，含每种类型的测试样例
Android 同项目academy/android/14-bthome-project.html同一项目的 Android 版，可跨平台互连
配套源码 · 可以直接编译本课的每一行代码都在 qingzhu-blue / examples / ios / bthome-mvp：Xcode 工程、协议层、扫描、连接、模拟外设、13 项协议自检全在里面。浏览器里也能先走 交互原型。教学服务 UUID 与 Android bthome-mvp 完全一致，iPhone 和 Android 手机可以互连。
对接协议的正确姿势不是找 SDK，而是读格式规范：确定 UUID → 确定设备信息字节 → 查对象 ID 表拿「类型 / 长度 / 有无符号 / 倍率」。这张表就是你写解析器需要的全部东西。
本步收束：规范在 bthome.io/format，对象 ID 表是解析的唯一天书。

第 2 步从广播包到 BTHome 数据：三层剥开

拿官方示例 020106 0B094449592D73656E736F72 0A16D2FC4002C40903BF13 剥三层。每个 AD 元素都是「长度 / 类型 / 数据」。

第 1 层 · AD 元素
02 01 06                  Flags: LE 可发现 + 不支持 BR/EDR（固定写 020106）
0B 09 4449592D73656E736F72  Complete Local Name = "DIY-sensor"
0A 16 D2FC4002C40903BF13    Service Data(16-bit UUID) ← BTHome 在这里

第 2 层 · 服务数据
D2FC                      UUID，按字节倒读 = 0xFCD2
40 02C409 03BF13          BTHome 数据

第 3 层 · BTHome 数据
40          设备信息字节 0100 0000
            bit0=0 不加密  bit2=0 定时广播  bit5-7=010 → v2
02 C409     对象 0x02 温度 sint16 LE 0x09C4=2500 ×0.01 = 25.00 °C
03 BF13     对象 0x03 湿度 uint16 LE 0x13BF=5055 ×0.01 = 50.55 %
重点 · 硬规则对象 ID 必须按数值从小到大排。接收端遇到不认识的 ID 就停止解析后面全部——排序是为了老接收端至少能读到前面认识的字段。v1 用的 UUID 是 0x181C / 0x181E，已废弃，新项目一律 v2 的 0xFCD2。
本课用到的对象ID类型倍率示例 → 结果
packet id0x00uint8100 2A → 42
电量0x01uint8101 5A → 90 %
温度0x02sint16 LE0.0102 C409 → 25.00 °C
湿度0x03uint16 LE0.0103 BF13 → 50.55 %
电压0x0Cuint16 LE0.0010C 020C → 3.074 V

iOS 侧的好消息：CoreBluetooth 已经替你剥好第 1、2 层——advertisementData[CBAdvertisementDataServiceDataKey] 直接给你 [CBUUID: Data]，FCD2 对应的 Data 就是第 3 层字节，不用自己拆 AD 结构。

本步收束：Flags + Name + Service Data(0xFCD2)；设备信息字节定版本；对象 ID 升序；小端 + 倍率 + 符号。

第 3 步一个 App 两个角色：模块怎么分

只装一个 App，靠入口切换角色。协议层是纯 Swift，不碰 CoreBluetooth 对象，好处是能直接写自检——不连真机也能验证解析器。

examples/ios/bthome-mvp/BTHome/
├── BthomeProtocol.swift    协议层（纯 Swift）
│                           对象 ID 表 / parse / encode / 教学 UUID / 13 项自检
├── BthomeScanner.swift     主端：扫描 FCD2 + 教学服务，按 identifier 合并，10s 标离线
├── SensorClient.swift      连接路线：connect → 发现 → 写 01 → 读回 BTHome 帧
├── SensorPeripheral.swift  从端：教学 GATT 服务 + 滑杆/正弦波数据源
├── BthomeApp.swift         SwiftUI：角色切换、扫描列表、连接面板、从端面板
└── Info.plist              蓝牙权限两键 + bluetooth-central/peripheral 后台模式
为什么要分协议层解析是整个项目最容易出错的地方（字节序、符号、截断）。把它做成不依赖 CBPeripheral 的纯函数，就能用官方测试样例当自检，不用两台手机也能验证解析器。源码里 DEBUG 构建启动即跑 13 项自检并打印到控制台。
本步收束：协议层纯净可测；扫描、连接、广播、UI 四块互不依赖。

第 4 步先写解析器，再用官方样例测

// BthomeProtocol.swift · 对象 ID 表：解析器需要的全部信息
static let objects: [Obj] = [
    Obj(id: 0x00, label: "序号", len: 1, signed: false, factor: 1,     unit: "",   min: 0,   max: 255),
    Obj(id: 0x01, label: "电量", len: 1, signed: false, factor: 1,     unit: "%",  min: 0,   max: 100),
    Obj(id: 0x02, label: "温度", len: 2, signed: true,  factor: 0.01,  unit: "°C", min: -40, max: 85),
    Obj(id: 0x03, label: "湿度", len: 2, signed: false, factor: 0.01,  unit: "%",  min: 0,   max: 100),
    Obj(id: 0x0C, label: "电压", len: 2, signed: false, factor: 0.001, unit: "V",  min: 0,   max: 65.535),
]                               // min/max：越界只标记，不丢也不直接信

static func parse(_ data: Data) -> Frame? {
    let bytes = Array(data)
    guard bytes.count >= 2 else { return nil }
    let info = bytes[0]
    let version = Int(info >> 5)
    guard version == 2 else { return nil }              // 只处理 v2
    if info & 0x01 != 0 { return Frame(encrypted: true, …) }  // 密文不解析
    var out: [Measurement] = []; var i = 1; var lastId = -1
    while i < bytes.count {
        let id = bytes[i]
        guard let o = obj(id) else { break }            // 规范：不认识就停
        if Int(id) < lastId { break }                   // 规范：必须升序
        guard i + 1 + o.len <= bytes.count else { break } // 截断包不越界读
        let raw = readLE(bytes, i + 1, o.len, o.signed)
        out.append(Measurement(obj: o, value: Double(raw) * o.factor))
        lastId = Int(id); i += 1 + o.len
    }
    guard !out.isEmpty else { return nil }
    return Frame(version: 2, encrypted: false, measurements: out, …)
}
重点 · 四个坑一次堵死① Swift 的 UInt8 天然无符号，但转 Int 做位运算时别混进有符号类型（Kotlin/Java 才需要 and 0xFF）；② 小端拼完要符号扩展，零下温度才对：if v & 0x8000 != 0 { v -= 0x10000 }；③ 不认识的 ID 立即停，不抛异常也不硬解；④ 边界检查防截断包崩溃。

本步收束：表驱动解析，小端 + 符号扩展 + 升序 + 未知即停 + 边界检查。

第 5 步扫描：只收 0xFCD2，按 identifier 合并

// BthomeScanner.swift
manager.scanForPeripherals(
    withServices: [CBUUID(string: "FCD2"), DemoProtocol.service],  // 系统层过滤
    options: nil)

func centralManager(_ c: CBCentralManager, didDiscover p: CBPeripheral,
                    advertisementData: [String: Any], rssi RSSI: NSNumber) {
    let serviceData = advertisementData[CBAdvertisementDataServiceDataKey] as? [CBUUID: Data]
    let frame = serviceData?[Bthome.uuid].flatMap { Bthome.parse($0) }
    if let frame, frame.encrypted { return }            // 本课不处理加密
    let connectable = (advertisementData[CBAdvertisementDataServiceUUIDsKey] as? [CBUUID])?
        .contains(DemoProtocol.service) ?? false
    guard frame != nil || connectable else { return }
    // 按 identifier 合并：同一台设备只留最新一条（C3）
    upsert(Device(peripheral: p, rssi: RSSI.intValue, reading: frame?.display, …))
}
重点 · 带 UUID 过滤的两个好处过滤在系统层做，App 不会被无关广播频繁唤醒；同时后台扫描必须带服务 UUID（C9），这里天然满足。取数据不用剥 AD 结构：CBAdvertisementDataServiceDataKey 直接给 UUID 之后的字节。

第 6 步从端边界：iPhone 发不出 BTHome 广播

平台边界 · Apple 官方CBPeripheralManager.startAdvertising iOS 6 的文档写明：只支持两个键——CBAdvertisementDataLocalNameKey 和 CBAdvertisementDataServiceUUIDsKey。没有 Service Data 键，iPhone 就塞不进 BTHome 的 0xFCD2 数据。前台广播预算约 28 字节，扫描响应另有约 10 字节只放名字；后台名字不发、UUID 进 overflow 区。

所以 iOS 版项目的角色分工和 Android 不同：

角色Android bthome-mvpiOS bthome-mvp
接收器（主端）扫描解析 BTHome完全胜任，扫真实设备/Android/ESP32
标准 BTHome 广播源addServiceData(FCD2, …)做不到；用 Android 手机/ESP32/Shelly 当源
模拟外设（教学）教学 GATT 服务教学 GATT 服务（同一套 UUID，跨平台互连）

编码器仍然要会写——教学 GATT 帧用的就是 BTHome 格式，而且读懂编码才懂解析：

// BthomeProtocol.swift · encode：升序 + 小端 + 倍率
static func encode(_ values: [(id: UInt8, value: Double)]) -> Data? {
    var out = Data([0x40])                              // v2，不加密，定时
    for item in values.sorted(by: { $0.id < $1.id }) {  // 必须升序
        guard let o = obj(item.id) else { continue }
        let raw = Int((item.value / o.factor).rounded())
        out.append(o.id)
        for k in 0..<o.len { out.append(UInt8(truncatingIfNeeded: raw >> (8 * k))) }
    }
    return out.count > 1 ? out : nil
}

// SensorPeripheral.swift · 广播只发名字 + 服务 UUID（iOS 仅支持这两键）
peripheral.startAdvertising([
    CBAdvertisementDataLocalNameKey: "QZ-BTHome",
    CBAdvertisementDataServiceUUIDsKey: [DemoProtocol.service],
])
热更新差异Android 有 AdvertisingSet.setAdvertisingData() 中途改数据不停广播；iOS 没有对应 API，改广播内容只能 stopAdvertising() 再 startAdvertising()（会闪断）。本课从端走 GATT 路线，读数变化直接体现在下一次读响应里，不需要动广播。
本步收束：iPhone 当不了标准 BTHome 广播源（官方两键限制）；接收器没问题；模拟外设走教学 GATT。

第 8 步连接和发数据：教学 GATT 路线（跨平台互连）

先把边界说清楚：BTHome 没有连接。规范目标是「用 BLE 发现包共享传感器数据和按键」，不提供控制通道。源码里这条教学扩展路线（不属于 BTHome 标准）与 Android bthome-mvp 用同一套 UUID 和指令，iPhone 与 Android 手机可以互连：

项UUID / 值说明
服务476CDF45-6063-43A1-B8E2-8C1FBED00601128 位随机 UUID，不冒用已登记 16 位 UUID
特征476CDF45-6063-43A1-B8E2-8C1FBED00602READ + WRITE
指令01主端写入 → 从端准备新读数 → 主端读回 BTHome 帧
// SensorClient.swift · 主端：一步步来
manager.connect(peripheral, options: nil)               // ① 连接
// didConnect → peripheral.discoverServices([DemoProtocol.service])
// didDiscoverServices → discoverCharacteristics([.sample], for: service)
// didDiscoverCharacteristicsFor → 检查 properties 含 read+write → 就绪
peripheral.writeValue(Data([0x01]), for: ch, type: .withResponse)  // ② 请求
// didWriteValueFor → peripheral.readValue(for: ch)              // ③ 读回
// didUpdateValueFor → Bthome.parse(ch.value!)                   // ④ 同一套解析

// SensorPeripheral.swift · 从端：CBPeripheralManager（iOS 6）
let ch = CBMutableCharacteristic(type: .sample, properties: [.read, .write],
                                 value: nil, permissions: [.readable, .writeable])
// didReceiveWrite：value == 01 → respond(.success)，准备新读数
// didReceiveRead：request.value = sampleBytes(当前温度) → respond(.success)
重点 · iOS 与 Android 的三个差异① 订阅（如果改用 notify 路线）iOS 一步 setNotifyValue(true, for:) 就完成「本机栈接收 + 设备 CCCD」两件事，Android 要两步（C7）。② iOS 没有 CCCD 写回调，从端用 didReceiveRead/didReceiveWrite 响应 ATT 请求，必须 respond，否则主端卡死。③ 读响应要处理 request.offset（长值分片读），源码用 dropFirst(offset)。

实际跑起来：从端启动广播 → 主端列表出现「可连接」设备 → 点进去等「已就绪」→ 点「请求新读数」→ 显示从端滑杆温度 + 50.55% 湿度 + 原始字节。从端拖滑杆到 -5.5 再请求，验证符号扩展。

本步收束：BTHome 本身不连接；教学 GATT 用同一套帧：connect → 发现 → 写 01 → 读回 → parse。跨平台同 UUID。

第 9 步验收清单：两台手机对时间线

A 机开从端（或拿真实 BTHome 设备 / Android bthome-mvp 当广播源），B 机（iPhone）开主端。按清单逐条打勾：

本步收束：9 条清单覆盖扫描、符号、更新、离线、后台、跨平台；与 HA 对标。

第 10 步做完之后往哪走

方向做什么关键点
加密bit0=1，AES-CCM，密钥 16 字节nonce = MAC(6) + UUID(2) + 设备信息(1) + counter(4)；接收端必须校验 counter 递增防重放；iOS 侧 MAC 不可得，加密设备对接要另想办法拿地址
真传感器ESP32-C3 + SHT4x，ESPHome 发 BTHome放电量对象 0x01，电池设备把间隔拉到 1s 以上
接 HAHA 装 Bluetooth 集成即自动发现你的设备名会成为 HA 里的实体名
标准 GATT 温度计1809 健康温度计 / 181A 环境感知2A1C 是 IEEE-11073 FLOAT、2A6E 是 sint16×0.01；配套 thermometer-mvp；下方解码工坊两种都能练
后台常驻bluetooth-central + RestoreIdentifier回到 C9：后台模式≠常驻，被终止靠状态恢复重启
需要双向广播不够用，回到 GATT 连接路线BTHome 不定义 GATT；正式产品按 C4–C8 自己定服务、特征和指令
本步收束：广播路线适合单向遥测；要配置、要历史、要可靠送达就走连接。

回顾项目速查

    
环节API / 规范最容易错

      
规范bthome.io/format 对象 ID 表拿了 v1 的 UUID

      
识别Service Data 0xFCD2写成 0x181C

      
设备信息bit0 加密 / bit2 触发 / bit5-7 版本没判版本就解

      
主端扫描scanForPeripherals 带 UUID + ServiceDataKey后台 nil 扫描扫不到

      
主端解析小端 + 符号扩展 + 未知即停 + 边界检查零下温度变 650 °C

      
从端边界startAdvertising 仅 LocalName + ServiceUUIDs以为 iPhone 能发 BTHome 广播

      
热更新iOS 无 setAdvertisingData，stop+start照搬 Android 热更新

      
连接路线connect → 发现 → 写 01 → 读回 → parse从端不 respond，主端卡死

      
验收双机 9 条 + 与 HA 对标 + 跨平台互连只测了正常值

      
源码examples/ios/bthome-mvp（13 项自检）只看不编译

    
说明本页为教学整理，平台边界对照 Apple startAdvertising 官方文档；演练为模拟，非真实设备通信。
