图解 BLE 链路：从扫描到一条温度数据

一个温度值怎么从传感器跑到手机屏幕上？这一页用比喻把整条链路讲透，每一步都配上对应的 Android API。读完再进正文，你会发现那些接口名突然都认识了。

难度：入门阅读约 15 分钟含交互演练配套：Android 开发指南

00先认清两个角色

BLE 通信里只有两种角色。温度传感器这类设备守着数据、等人来取，叫 外设（Peripheral）；手机这类主动去找设备、发起连接的一方，叫 中心设备（Central）。你的 Android App 几乎总是中心设备。

打个比方把 BLE 世界想成一间大教室：传感器是坐在座位上、知道答案的同学；手机是走动提问的老师。同学不离开座位，只负责「让人找到」和「回答问题」；老师负责找人、建立对话、拿到答案。整条链路就是「老师怎么找到同学并拿到那个温度值」。

01广播与扫描：设备怎么被找到

传感器没连上任何手机之前，唯一能做的事是周期性地对外广播（Advertising）：每隔一段时间发一小包数据，内容通常是设备名、服务 UUID、厂商数据。手机侧调用 BluetoothLeScanner.startScan() 监听这些包，每收到一个就回调一次 onScanResult()——App 里的设备列表就是这么来的。

打个比方广播就是同学隔一阵举一次手：「我在这儿，我是温度计。」扫描就是老师竖着耳朵听谁举手。注意两点：举手牌只有 31 字节，写不了几个字，所以广播内容要精简；举手太勤费电、太慢难被发现，广播间隔是产品要做的取舍。
ScanActivity.ktKotlin
val scanner = bluetoothAdapter.bluetoothLeScanner
val filter = ScanFilter.Builder()
    .setServiceUuid(ParcelUuid.fromString("00001809-0000-1000-8000-00805F9B34FB")) // 温度服务
    .build()
val settings = ScanSettings.Builder()
    .setScanMode(ScanSettings.SCAN_MODE_LOW_LATENCY) // 用户正在等结果时用低延迟
    .build()
scanner.startScan(listOf(filter), settings, scanCallback)
// scanCallback.onScanResult(result) → result.device 可用于建连，result.scanRecord 是原始广播
新手常踩Android 7.0 起 30 秒内启停扫描超过 5 次会被限流；8.1 起熄屏时不带过滤器的扫描会被暂停。扫描要统一入口、带 ScanFilter、用完即停。详见 过滤与后台扫描。

02连接：从「喊话」切换到「对话」

在扫描结果里选中设备后，调用 device.connectGatt() 发起连接。连上之后规则变了：外设停止广播，双方按约定的周期交换数据。这个周期叫 连接事件，节奏由三个参数决定：

  • Connection Interval：多久碰一次头（7.5ms ～ 4s）。越小延迟越低、越费电。
  • Slave Latency：外设没数据时可以跳过几次事件。省电的关键。
  • Supervision Timeout：多久没碰头就判定断线。
打个比方扫描阶段是「满教室喊话」，连接之后改成「拉着手说悄悄话」：约好每 30ms 碰一次头，有话说话、没话各忙各的；传感器还能申请「没变化时让我翘几次碰头睡会儿」。BLE 省电的本质不是不干活，而是约好了才干活。
ConnectStep.ktKotlin
val gatt = device.connectGatt(context, false, gattCallback) // false = 直接连接，用户在等

override fun onConnectionStateChange(gatt: BluetoothGatt, status: Int, newState: Int) {
    if (status == BluetoothGatt.GATT_SUCCESS && newState == STATE_CONNECTED) {
        gatt.discoverServices() // 连上 ≠ 能用，下一步先看数据模型
    }
}
记住STATE_CONNECTED 只代表链路建立。服务没发现、订阅没完成之前，业务上都不算「就绪」。断线重连要当全新会话处理，别复用旧 GATT 对象。

03GATT：设备里的数据长什么样

连上之后，设备把它的数据组织成一棵三层树，这套规范叫 GATT：

  • Service（服务）：一组相关功能的集合，比如「健康温度计」「电池」。
  • Characteristic（特征）：真正放数据的叶子节点，比如「温度测量值」。
  • Descriptor（描述符）：特征的附加配置，最重要的是控制订阅的 CCCD。

每个节点用 UUID 标识。蓝牙联盟给常见功能分配了 16 位短 UUID：温度测量是 0x2A6E，电池电量是 0x2A19。看到标准 UUID，不用问厂商就知道数据格式。

打个比方GATT 就是设备随身携带的一个文件柜：Service 是抽屉（温度抽屉、电量抽屉），Characteristic 是抽屉里的文件夹（温度值、报警阈值），UUID 是每个抽屉和文件夹上的统一标签——全世界的温度计都用同一套标签，所以手机不用猜。discoverServices() 就是「把柜子拉开看一遍」，不看就伸手乱摸是要碰壁的。
DiscoverStep.ktKotlin
override fun onServicesDiscovered(gatt: BluetoothGatt, status: Int) {
    val service = gatt.getService(UUID.fromString("00001809-0000-1000-8000-00805F9B34FB"))
    val tempChar = service?.getCharacteristic(UUID.fromString("00002A6E-0000-1000-8000-00805F9B34FB"))
    // 16 位 UUID 的完整形式：0000xxxx-0000-1000-8000-00805F9B34FB
}

对特征有三种基本操作：Read（问一次答一次）、Write（下发配置，比如报警阈值）、Notify/Indicate（设备主动上报）。温度这种持续变化的值，靠轮询 Read 又慢又费电，正确姿势是订阅。

04订阅：那朵「小红花」贴在哪

订阅的开关不在特征本身，而在它旁边的描述符 CCCD（Client Characteristic Configuration，UUID 0x2902）。往里写不同的值，含义不同：

写入值（小端）含义区别
01 00开启 Notify设备发了就走，不等确认，快
02 00开启 Indicate每条要等手机回「收到」才发下一条，可靠但慢
00 00关闭停止上报
打个比方CCCD 是文件夹边上的一张订阅卡：贴上花（写 01 00）等于告诉设备「以后有变化主动告诉我，不用我来问」；贴大红花（02 00）还要求「每汇报一条，等我签收再报下一条」。很多「收不到通知」的 bug，根因就是卡没贴、贴错了文件夹，或者只贴了自己这一半。
SubscribeStep.ktKotlin · 两步都要做
// 第 1 步：打开本地开关（只影响手机侧分发，不会通知设备）
gatt.setCharacteristicNotification(tempChar, true)

// 第 2 步：写远端 CCCD，设备才会真的开始发
val cccd = tempChar.getDescriptor(UUID.fromString("00002902-0000-1000-8000-00805F9B34FB"))
gatt.writeDescriptor(cccd, BluetoothGattDescriptor.ENABLE_NOTIFICATION_VALUE) // 01 00

override fun onDescriptorWrite(gatt: BluetoothGatt, d: BluetoothGattDescriptor, status: Int) {
    // status == GATT_SUCCESS 才算订阅完成，此前设备可能已经开始发数据
}
override fun onCharacteristicChanged(gatt: BluetoothGatt, c: BluetoothGattCharacteristic, value: ByteArray) {
    // 2A6E：小端 sint16，除以 100 得摄氏度。2450 → 24.50°C
}
高频故障只做第 1 步不写 CCCD，是「收不到通知」的头号原因。另外订阅要等服务发现完成、写操作要排队（一次只提交一条属性操作），详见 Notify 与 CCCD、命令队列。
